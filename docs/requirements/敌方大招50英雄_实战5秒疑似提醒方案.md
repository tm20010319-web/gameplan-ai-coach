# 敌方大招：首批50英雄、实战5秒疑似提醒方案

整理日期：2026-09-18。本文是拟实施方案与范围清单，不表示50位英雄已经实现或通过验收。

## 2026-09-18 实施状态

已完成知识库机制对照、50英雄范围接口、独立疑似提醒、知识库冷却范围及起手时间区间显示，并更新本地 8767 监控服务。详细参考见 [首批50英雄知识库识别参考](首批50英雄知识库识别参考.md)；真实复测记录见 [本轮实施与验证报告](../../work/implementation-20260918/report.md)。

当前推理路径仍是 Ollama Qwen3-VL、OCR 与短时光流跟踪。下文的轻量动作模型、50位英雄训练和逐英雄独立验收尚未完成。最新服务复测中敖隐、高渐离出现疑似提醒，孙策仍漏报，没有新增确认释放记录；尚未达到稳定5秒提醒或精准冷却识别。回归测试通过仅说明程序行为符合测试约束，不代表实战准确率达标。

## 已确认的需求

- 输入：手机游戏实战投屏到当前 Windows 电脑。
- 首批范围：50位英雄的大招，由项目方整理名单。
- 提醒目标：敌方释放后5秒以内。
- 取舍：优先给出明确标注的“疑似开大”提醒，随后核实；允许存在未确认候选。
- 冷却来源：按用户之前提供、项目中现有的知识库取值；当前技能说明与基础冷却入口为 `resources/knowledge/skill_catalog.json`。Ollama及动作识别模型只提供释放证据，不生成、猜测或改写冷却数值。
- 冷却计时：只有确认释放且能确定计时起点时，才按知识库进入“估算冷却”；无法得知装备、技能等级或刷新时，不标成真实精确冷却。
- 本次细化的是大招方案。闪现仍属于原项目需求，需要独立的瞬间位移识别与正反例验收，不计入50位大招覆盖率。

## 核心架构

推荐采用经过游戏画面训练的轻量目标检测/跟踪与短序列动作识别，Ollama用于有余量时的补充复核和离线分析。

1. **采集与短期缓存。** 保留最近约3秒的原始时间戳画面，测试10–15帧/秒的检测输入；最终频率由最坏多人团战性能决定。实时路径不按固定片段无限排队，短时缓存用于补足起手前后证据。
2. **本局身份建立。** 利用加载和战绩面板，结合英雄头像与昵称建立己敌对应。要求跨帧一致，对昵称错字进行有证据的纠正。不能仅凭阵容名单给战场角色指定身份。
3. **持续目标跟踪。** 对当前画面敌方角色维护短时轨迹；昵称被“霸体”“击飞”等状态字遮住时，结合外观、运动和血条位置延续已确认身份。长时遮挡、交叉重叠或跟踪漂移时降为未知，避免串人。
4. **按英雄条件识别动作。** 仅处理本局敌方且当前可见的目标，最多对应5位敌人；从角色周边短视频识别该英雄的大招起手、持续与结束，并与普攻、小技能、召唤师技能区分。目标检测器负责找人，时序分类器负责判断动作，不能拿通用检测器直接声称支持50位大招。
5. **先疑似、再确认。** 动作有相关证据且敌方归属可靠时，立即输出疑似提醒；后续画面增加证据后升级。不同英雄使用独立校准门槛，不能直接把大模型输出的0.95当成95%正确率。
6. **Ollama不阻塞即时提醒。** Qwen仅限频复核疑难候选。当前8B模型实际驻留约13GB显存，而显卡总计16GB；必须测试与轻量模型并存时的显存及GPU竞争。余量不足时关闭实时Qwen复核，使用离线复核，避免挤占5秒目标。

当前硬件为 NVIDIA GeForce RTX 5070 Ti 16GB、48GB系统内存。它支持开展上述本地方案的性能验证，但未经训练和实测，不能据此保证50位英雄都在5秒内可靠识别。

## 知识库冷却取值规则

- 按英雄对应的大招条目读取 `base_cooldowns_s`、`cooldown_text`、`cooldown_kind`、`cooldown_formula`、`cooldown_note` 和资料核对标记，保留原有数值与特殊机制说明。
- 知识库有多个技能等级的冷却档位时，已确认大招等级则采用对应档位；未确认时保留档位信息并明确估算依据，不把英雄达到4级或模型猜测当成大招等级证据。
- 起点及多段、刷新、动态冷却按知识库已明确的规则处理；缺少必要条件或条目待核对时显示“冷却待确认”，不自行补一个秒数。
- 确认后的剩余时间根据知识库冷却和真实释放/冷却触发时刻计算，扣除识别等待期间已经过去的时间，不从字幕出现时重新计满。
- 疑似开大仍先提醒；没有确认的候选不产生已确认冷却记录。

## 提醒与计时状态

| 状态 | 用户看到的内容 | 是否开始冷却计时 |
| --- | --- | --- |
| 有相关证据，尚未确认 | “敌方高渐离疑似开大” | 否 |
| 确认起手及释放时间 | “敌方高渐离已开大” | 按用户知识库的冷却值与机制显示估算 |
| 只确认正在使用，没看到起手 | “敌方高渐离正在使用大招，起手时间未知” | 不编造起点 |
| 候选被反证或无法继续确认 | “未确认”，短暂显示后撤下 | 否 |
| 已记录释放，但冷却机制不明 | “已开大，剩余冷却未知” | 否 |
| 估算倒计时结束 | “预计已冷却” | 不等于实际技能已可用 |

疑似提醒不占用已确认事件的去重锁，不阻止后续真实释放。新的可靠证据可以修正释放时间。刷新、连续释放及多段技能按英雄机制处理，不能用一个固定冷却下限一律拒绝再次释放。

等级未知可以保留带不确定性的候选，不伪造等级；清楚读到未解锁等级时不能升级为确认大招。离开视野不代表没有开大，未观察到释放也不代表敌方有大招。

## 数据与验证

目前两个用户录像和19张战斗回归图适合复现已发现的问题，不能覆盖50位英雄的皮肤、遮挡和团战场景。现有技能介绍JSON提供机制资料，不能替代训练视频。

建议先按每位英雄50–100次独立释放事件收集初始样本，并配套普攻、小技能、其他英雄特效、镜头移动等负例；这是启动数据量建议，不是足以达标的保证。每个事件保留起手前后连续画面，标注人物身份、敌我、起手时间、皮肤和可见性。数据不足的英雄应标记为待验证，而非写进名单便宣称支持。

训练、调参、最终测试按完整录像/对局分开，同一段视频的相邻帧不能分别放进训练集与测试集。验证需包含不同皮肤、清晰度、多人重叠、视角移动和投屏延迟。先修复敖隐提前误报、高渐离特效拒绝、孙策身份丢失这三个已知问题，再在同一架构内分组完成全部50位英雄验收。

建议的首轮验收目标，尚未实测达成：

- 对独立测试集中画面可辨认的真实释放，至少90%在5秒内产生疑似或确认提醒；漏检和迟报都算未达标，不能只统计成功检出的样本。
- “确认释放”单独统计精确率，建议目标至少95%；疑似误报单独统计每10分钟出现次数，并根据实际体验确定可接受上限。
- 每位英雄分别报告数据量、召回率、确认精确率、提醒延迟、起手时间误差和误报次数，不能只提供被容易英雄拉高的总体平均数。
- 5秒从可核对的游戏释放时刻到界面出现提醒，包含投屏、采集、排队、识别与显示。若只能测到PC收到画面之后的耗时，必须单列投屏延迟，不能声称完整端到端达标。
- 屏幕外且没有可靠可见线索的释放单列为不可观察范围，不纳入“精准识别”的能力承诺。

## 实施顺序与交付物

1. 建立50位英雄的机制配置和样本清单；改造疑似/确认状态、记录候选及拒绝原因，修复误报污染后续事件的问题。
2. 在真实投屏上验证采集、跟踪、短序列检测的延迟预算；减少重复OCR，并根据显存测试决定Qwen能否同时驻留。
3. 收集与标注50位英雄数据，训练/校准轻量模型。逐组验收，持续保留未达标英雄清单。
4. 用独立完整对局验收漏报、误报、5秒内提醒率；接入基于确认事件的冷却估算。

需要交付的内容包括：50英雄范围清单、样本与标注规范、模型及版本记录、实时疑似/确认提示、逐英雄测试报告和性能报告。没有完成这些验证之前，只能称为实验支持，不能承诺“精准识别50位英雄”。
