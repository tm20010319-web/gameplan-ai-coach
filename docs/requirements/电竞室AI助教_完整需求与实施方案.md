## 1. 项目目标与统一口径

### 1.1 产品目标

面向电竞室中的玩家和教练，持续观察电脑上的游戏画面，把可见的阵容、对位、技能、兵线、资源和时间变化转成可执行的文字建议，形成“赛前选人 → 加载计划 → 局中提醒 → 技能冷却跟踪 → 行为记录 → 赛后复盘与扫码查看”的完整流程。

目标运行方式是：用户选择观察目标并启动一次监测后，系统自动采样、识别阶段、记录已支持事件、更新或撤销建议。人工录入用于补录、纠错和演示；正常自动流程不依赖逐次上传截图、点击分析或填写敌方技能施放时间。

当前游戏示例和知识资料围绕《王者荣耀》5v5。首期按单游戏、固定界面配置、单路会话 Demo 设计；其他游戏、不同视角和多路并发需单独适配与验收。

### 1.2 本次明确的重点

用户已明确：**敌方技能释放时间由系统从游戏画面自动识别，人工补录或纠正；系统记录释放时间，在有可靠冷却依据时提供倒计时，并在预计就绪时提醒。** 只完成手动计时不算此项需求完成。

先把需求写清楚，再开展代码工作。此前已产生的手动计时相关代码与测试属于预研，是否复用须按本文件对照；本文不将其标记为自动识别功能交付完成。

### 1.3 统一原则

| 主题 | 整合后的口径 |
| --- | --- |
| 画面来源 | 默认观察电脑上用户指定的游戏窗口、显示器或区域；截图和本地录像用于测试，scrcpy / OBS 可作为电脑上的画面来源；不要求摄像头 |
| 视觉与文字分工 | Qwen3-VL-8B 是候选视觉核心，按需结合 OCR / 专用检测器；规则和知识库判断事实与条件，外部文本模型只生成有依据的简短建议 |
| 对线与阵容 | BP 同路对位、清线和换血评价与全局阵容搭配分开；团战作用不能替代对线优势 |
| 提醒呈现 | 默认文字 HUD，不播报语音、不联动灯光；局中少量高价值提示，技能计时独立常驻，不抢操作焦点 |
| 自动操作 | 只提供观察、记录与建议，不自动控制游戏 |
| 未知信息 | 保留未知、范围和来源，不把“未看到”当作“未发生”，不把预计冷却结束当作确认技能可用 |
| 复盘归因 | 结算数据只能支持数据摘要；具体团战或执行判断需要可关联的过程证据 |
| 完成判定 | 以声明范围内的真实画面和指定硬件验收；接口测试、人工示例和模拟模型不能替代自动识别验收 |
| 性能数字 | 旧文档中的 50ms 投屏、300–600ms 推理、2 秒建议及 5 秒战报均是历史目标或优化方向，不是已验证承诺 |

## 2. 完整使用流程与交付范围

### 2.1 用户完整流程

| 阶段 | 用户 / 游戏动作 | 系统与界面目标行为 |
| --- | --- | --- |
| 观察就绪 | 选择电脑游戏窗口或区域，开始观察 | 标明采集目标与状态，自动识别阶段和玩家上下文；不确定时允许纠正 |
| BP 选人 | 敌方选人、预选或禁用变化，用户仍可选人 | 核对可能的同路对位，显示最多 3 个有依据且当前可选的候选 |
| 自己锁定 | 用户确定英雄 | 撤下换英雄候选，切换为当前英雄的对位打法 |
| 阵容加载 | 双方阵容完整出现 | 给出开局计划、阶段目标和个人团战职责 |
| 局中事件 | 已支持的资源、对线或团战条件变化 | 持续维护状态，只在必要时提醒，前提过期立即撤下建议 |
| 敌方施放技能 | 已支持技能获得可靠画面证据 | 自动记录释放时间，结合冷却依据计时，到点提醒；错误可人工修正 |
| 主动提问 | 点击“这波怎么打 / 为什么这样建议” | 使用当前有效状态回答，展示依据与未知项 |
| 结算 | 结束与结算页稳定出现 | 停止本局活动提醒，提取可见结果，生成有证据的复盘与训练目标 |
| 扫码查看 | 查看或分享战报 | 手机打开可访问的战报页面并保存海报 |

### 2.2 功能范围

| 功能 | 用户得到的辅助 | 触发条件 / 依据 | 范围 |
| --- | --- | --- | --- |
| BP 对线压制选人 | 最多 3 名同路候选及清线、换血、压制条件，说明等级与装备阶段限制 | 敌方同路对位已确认或条件明确，用户仍可选人，对位资料已核验 | 首期核心 |
| 己方阵容搭配 | 独立展示前排、控制或保护方面的全局建议 | 己方英雄与职责标签可靠；不得替代对线评价 | 独立扩展 |
| 实时对线判断 | 提示争取线权、短换血、控线发育或停止前压，并显示当前依据 | 对位身份与必要的血量、等级、兵线、位置等状态可靠 | 首期验证少量事件，精细技能窗口为进阶 |
| 开局与分阶段计划 | 一级站位、防守防抓、前中后期目标和团战职责 | 视觉确认阵容、用户分路及阶段，已支持事件持续更新 | 首期生成初始计划并按已支持事件调整 |
| 出装/技能应对方向 | 根据已识别的阵容与威胁提示应对；有版本依据时给具体候选 | 当前视觉信息与已核验机制资料共同支持 | 首期随阵容确认提供要点；基于可见经济/装备变化的动态调整为进阶 |
| 目标与补给提醒 | 资源准备、回城前确认安全与停止追击等一条短提示 | 必要画面证据持续有效；目标、血蓝、兵线或威胁信息可确认 | 在首期事件通过后分批扩展 |
| 团战准备 / 拉扯 / 撤退 / 团后转资源 | 一条主动作与关键理由，有证据时提供备用动作 | 人数、血量、技能、位置、兵线和资源等相关前提足够 | 首期验证 1 类团战准备或撤退事件；其余逐类验收 |
| 敌方技能自动计时 | 自动记录施放、倒计时与预计就绪提醒，支持人工纠错 | 英雄、技能、事件时间和冷却依据可靠 | 本次明确新增；以第 4 章支持清单及专项验收为准 |
| 当前画面文字问答 | 点击“这波怎么打 / 为什么这样建议”，获得当前状态的回答 | 最新视觉状态及可追溯依据，返回时重新校验有效性 | 固定问题首期；自由输入为扩展 |
| 提醒开关与表达风格 | 可关闭主动提醒、继续主动提问；简短或展开依据 | 暂停观察与关闭提醒分别管理；风格不改变事实与结论 | 首期 |
| 建议后的行为回顾 | 展示建议后观察到的推线、后撤、交战或转资源行为 | 可关联同一玩家/队伍的连续轨迹与结果 | 日志基础首期；自动判断为进阶 |
| 赛后点评与训练目标 | 可见战绩摘要、证据支持的行为点评、下一局一个可执行目标 | 结算数据及可用事件日志 | 首期；无过程证据时用通用练习建议 |
| 海报与扫码查看 | 战绩、AI 点评和训练目标组成可保存的战报 | 战报生成完成且手机可访问页面 | 首期 |

首期覆盖是经验证的英雄、对位与事件子集。小地图多人持续追踪、完整敌方动向、复杂装备联动、精细团中指挥和自动行为归因分批扩展；不能把知识库条目数量当作视觉覆盖率。

## 3. 战术建议与交互需求

### 3.1 BP 对线压制与局中对位判断

目标：在玩家仍可选择时，针对敌方同路英雄给出候选，说明谁更容易清线、争取换血收益或取得线权，以及优势成立的条件。英雄池与熟练度用于资格筛选和选择偏好，不能将“有团控、能保护后排”直接视为对线压制依据。

处理流程：

1. **确认 BP 状态**：从连续画面自动识别双方阵营、敌方已锁英雄、己方已选英雄、禁用列表和用户选人状态。预选英雄只标为暂定，不当作最终阵容；用户无需手动录入每次选人。
2. **确定玩家需求**：优先从可靠视觉信息确定当前分路；用户可选提供的擅长英雄和可用英雄池用于排序。分路未知时给带分路标签的参考候选，不能假定用户的分路、英雄可用性或熟练度。
3. **生成并过滤候选**：按“游戏版本 + 分路 + 我方候选 + 敌方对位 + 等级/装备阶段”查询已审核对位资料，再按当前模式规则剔除禁用、占用和已知不可用英雄。只覆盖英雄名称但没有该对位资料时，不补造压制结论。
4. **按对线条件排序**：比较清线速度与安全性、射程、消耗/续航、短换血和持续对拼、技能空档、等级节点、兵线依赖及防抓代价。说明评价适用的阶段与熟练度条件，不显示未经验证的压制分数或胜率提升。
5. **输出最多 3 名**：每名显示“我方英雄 vs 敌方对位”、可争取的对线优势、具体打法和优势失效条件。候选不足时按实际数量展示。
6. **随 BP 更新**：实际对位改变、换线、禁选变化或用户锁定后重新校验。用户锁定后撤下换英雄建议，转为当前英雄的对线打法；进入对局后以实时状态判断能否执行。

对位优先支持对抗路、中路和发育路。发育路遇到辅助在场时须结合局部人数和双人配合，不能机械套用射手单挑结论。打野、游走通常没有固定单人对线，不强制给出同路压制评级。多分路英雄在 BP 时只能作为可能对位，进入对局后需要用连续画面确认。

卡片结构示例（英雄对位强弱需当前版本验证）：

> **中路对位 · 王昭君 vs 妲己**  
> 对线计划：尝试用范围技能兼顾清线与消耗，保持安全距离争取线权。  
> 执行条件：关注双方等级、血量、技能状态和兵线；对方控制条件不明时避免近身换血。

每次推荐保留候选、敌方对位、分路、对线维度、等级/装备阶段、优势条件、失效条件、资料 ID 和 BP 状态版本。不能根据“敌方对抗路锁定关羽”就直接认定己方中路英雄可以压制其对线。

#### 3.1.1 局中通过视觉判断当前能否压制

将“BP 时的对位潜力”与“此刻的压制机会”分别记录。系统持续观察同路双方和附近威胁，输出 `push`（争取线权）、`trade`（条件允许时短换血）、`hold`（控线/稳线）、`retreat`（停止前压）或 `unknown`（证据不足），并附具体依据与有效期。

- 看双方英雄与实际路线，确认对手身份，换线后重建对位。
- 看等级、血量/蓝量、可见装备以及兵线的数量和位置；不能因英雄资料占优就忽略当前状态劣势。
- 看双方与兵线、防御塔和支援入口的相对位置；兵线优势不直接等于可以越塔。
- 技能空档需要可靠的技能事件、连续追踪及版本规则。画面没看见施法不代表技能可用；不能靠 1–2 FPS 的低频采样承诺识别所有瞬时技能。
- 对方打野未出现时，只能说明其位置未知；不得推导为安全。明确支援威胁出现或关键依据过期后，撤下压制提示。
- 输出“先清线再消耗”“等关键技能空档再短换血”“兵线劣势时先后撤”等可执行建议；未知前提直接影响决策时保持观察。

对线成效评估使用可见且连续记录的清线、换血、兵线控制和回城/阵亡事件；有可靠数据时再统计对位经济或经验差。不能仅凭最终 KDA、团战表现或整局胜负认定压制成功。

### 3.2 阵容加载、开局与阶段计划

视觉确认双方锁定后，自动生成一张 60–100 字的初始摘要卡；随后根据已确认的游戏阶段、阵容修正和已支持事件调整相关内容。详细内容按需展开，重点包括：

- **己方怎么发挥**：围绕先手控制、保护核心、消耗或边线牵制等已确认阵容特点提出计划。
- **敌方主要威胁**：说明值得注意的突进、控制或持续输出来源，并给出与用户英雄相关的应对。
- **对线注意事项**：依据对位资料描述换血条件、技能保留、防抓站位；对位不确定时标注条件。
- **开局计划**：一级守入口、观察入侵、防止落单等有依据的准备建议。敌方实际开野方向未知时，不把计划写成已发生事实。
- **前中后期目标**：给出当前阵容通常适合的节奏，并说明经济、装备或局势变化会影响执行条件。
- **个人团战职责**：前排开团或保护、后排输出位置、刺客等待机会等，结合英雄资料解释。

首期从加载画面生成初始计划，并通过持续视觉观测判断其是否仍适用；更新范围限于已验证的字段和事件。复杂兵线、经济、装备与技能联动逐步扩充。无法从屏幕确认队友或敌人的技能冷却时，不声称“某英雄有大/没大”；可表达为“确认关键技能可用后再接团”。

### 3.3 团战准备、交战与团后收益

团战功能按团前准备、交战中的行动与团后转资源组织。首期优先验证“等人再开”“明确劣势时后撤”等保守事件，精细接团、技能衔接与团中追踪作为进阶能力。以下决策均按必要观测能力逐类启用：

| 决策 | 必要判断 | 提示示例 |
| --- | --- | --- |
| 接团 | 同一交战区域及可支援人数、关键血量/技能、位置或线权、目标价值满足已验证规则 | “先推中线，确认关键技能可用后再接目标团。” |
| 拉扯 | 已确认正在接近/交战，且存在血量、位置或技能上的明确限制 | “先拉开距离，等队友到位再接。” |
| 撤退 | 可靠的局部人数劣势、核心低血量/缺席或迫近威胁，且建议仍可执行 | “队友尚未到位，先退到安全位置。” |
| 换资源 | 当前目标难以安全争夺，另一侧资源可见、可到达且风险已评估 | “暂缓争夺目标，优先处理另一侧已确认安全的兵线。” |

不强制四选一：增加 `observe`（继续观察）和 `no_advice`（本次不提示）状态。人数、技能、位置等决定性前提未知时，不生成确定的强开或换资源指令。更高的模型自报置信度不能替代缺失事实。

统一建议结果至少包含 `decision`、`urgency`、`message`、`evidence_ids`、`conditions`、`state_version` 和服务端确定的有效期。备用动作只在依据足够时显示。电脑游戏画面正常显示，局中侧栏同时展示一条主建议，沿用第 5.5 节的过期、去重和降级机制。

按阶段细化用户收到的建议：

- **团前准备**：检查队友是否到位、自身血蓝和可见技能、兵线与目标条件；提醒“先等输出位到场”“先处理兵线再靠近”。
- **团中行动**：在可靠追踪基础上判断拉开距离、保护被切后排或停止追击。战斗变化快，只有实测能及时送达的事件才启用；不做逐帧技能操作指令。
- **团后收益**：结合已确认的存活状态、兵线、防御塔和目标情况，建议推线、转塔、准备资源或回城；胜利动画或一条击杀提示不足以证明可以安全开龙。
- **个人职责**：结合玩家英雄，说明应该保护谁、等待什么进场条件或保留哪类技能；没有可靠冷却证据时，不声称他人关键技能可用。

### 3.4 资源、补给、出装与文字问答

| 功能 | 触发/必要依据 | 提示示例 | 上线条件 |
| --- | --- | --- | --- |
| 目标准备 | 可读目标倒计时、玩家位置、必要的兵线/队友信息 | “先处理中线，再确认队友能否到场。” | 已支持目标规则及倒计时识别通过 |
| 防抓与停止追击 | 敌人最后可见位置、当前可见支援、追击区域与自身状态 | “支援已到河道，先停止前压。” | 只针对明确可见威胁或标注为未知的风险，不报隐藏敌人精确位置 |
| 回城补给 | 自身血蓝、兵线、当前敌方威胁与位置 | “先退到安全位置，再考虑回城补给。” | 不把低血量单独等同于原地回城条件 |
| 团后推塔/转资源 | 可确认的存活状态、可见兵线、塔/目标状态及己方状态 | “兵线已到，先评估推塔，避免追得过深。” | 对资源可达性与风险有足够依据 |
| 出装方向 | 已确认双方英雄与伤害/回复机制、自己可见装备和经济 | “对方回复较多，可考虑补充重伤；先核对已有装备与经济。” | 版本资料可靠；数据不足时只解释方向，不断言立刻购买最优 |
| 当前局面问答 | 用户点击“这波怎么打 / 为什么先退 / 装备怎么选”，关联最新视觉状态 | 用一条行动句加当前证据回答 | 首期可做固定问题；自由文字提问逐步扩展 |
| 玩法与机制解释 | 用户主动提问、版本明确且知识条目已审核 | 说明技能、装备作用与适用条件 | 不把一般机制解释冒充当前画面已经发生的事实 |
| 情境反馈与训练目标 | 有证据的事件、结束状态或赛后日志 | “这次后撤保住了状态；下一次继续先看队友位置。” | 结果因果不充分时只描述行为；鼓励性表达不虚构表现 |

所有例句都表示功能形式，只有前置条件满足才展示；它们不是对任意对局均有效的固定指令。

### 3.5 提醒优先级与表达风格

1. 同时出现多个候选建议时，优先处理迫近风险和原建议失效，其次是短时间有效的团战/资源准备，再是对线、出装和一般解释。频率上限与冷却时间可配置。
2. 主动提示关闭后，仍可持续采集并更新状态，只有用户提问才回复；“暂停观察”则停止采样并使动态建议失效。界面明确区分两个开关。
3. 问答绑定请求时的对局、状态版本、证据时间与观察范围；回答返回时再次校验。用户重复提问不沿用已经过期的战术结论。
4. “为什么这样建议”展示本条建议的必要依据和未知项。原因解释引用已确认事实，不能让文本模型自行补造隐藏技能或敌方位置。
5. 表达风格只改变长度、解释方式和语气，不改变行动结论、事实和未知项。鼓励话术放在低打扰时机，不给玩家贴负面标签。
6. 有可靠事件跟踪时，简短说明一条建议被撤销的原因；“未提醒”与“未在画面中看到”不等同于事件没有发生。

### 3.6 建议记录与行为回顾

首期记录建议、显示时间和证据；进阶版本在可靠追踪基础上关联建议后的可观察行为：

- 推线后接团：记录兵线变化、移动方向以及何时靠近目标区域。
- 撤退：记录是否拉开距离或进入可确认的安全位置。
- 击杀后转资源：记录随后可见的移动目标、攻击对象和资源变化。
- 交战结果：只记录已确认的死亡、目标或防御塔变化；不知道的经济变化不补齐。

结果使用“观察到与建议一致的行为 / 观察到不同的行为 / 证据不足”，不判断用户主观意图。建议时间窗之外的行为不强行关联；局部画面无法代表整队行为。

赛后将有证据的事件整理为“时间点 → 当时局面 → 提示 → 可观察行为 → 已知结果”，再提出一个可执行的训练目标。若没有足够过程证据，可提供“争夺目标前先确认队友位置”等通用练习，并标明其属于通用建议。一次交战输赢不能直接证明建议正确或用户执行有误。

## 4. 敌方技能自动记录与冷却提醒

本章保留完整的自动识别、计时、纠错与验收规则。正常流程无需逐次人工登记；只有手动计时可用时，仍应标记自动识别需求未完成。R1～R7 为技能功能编号，A01～A15 为专项验收编号。

### 4.1 场景与范围

#### 4.1.1 正常使用流程

1. 用户选择游戏画面来源，启动本局连续观察；确认或修正系统识别出的双方阵容。
2. 系统发现敌方某英雄施放技能，核对英雄、技能和证据后，自动记录该次释放。
3. 系统查询该英雄该技能在本局适用的冷却规则，结合已知技能等级和冷却影响因素判断能否计时。
4. 能确定冷却时，自动展示倒计时；只能确定范围时，展示预计范围；无法计算时，显示“已记录释放，冷却未知”。
5. 冷却将结束时给予轻量提示，到点提醒“敌方 ×× · ×× 技能预计可用，请留意”。
6. 用户发现误差时，可修改英雄、技能、释放时间或冷却依据，也可撤销误记录；修改同步到同局大屏。

#### 4.1.2 功能范围

| 范围 | 本需求口径 |
| --- | --- |
| 主要对象 | 敌方英雄主动技能；优先支持大招、关键控制和位移技能 |
| 正常入口 | 连续游戏画面中的自动识别；单张截图只辅助核对，不能凭静态画面虚构先前的释放时间 |
| 人工兜底 | 补录漏掉的施放、只登记已知剩余时间、修正或撤销错误记录 |
| 展示 | 工作台与同局大屏的常驻技能面板；提示不抢焦点、不阻塞游戏操作 |
| 提醒方式 | 默认文字和颜色提示；语音、系统通知和手机推送不列入本次范围 |
| 技能覆盖 | 先建立经验证的英雄 / 技能清单，在界面标明覆盖范围；知识库有该英雄不代表已支持自动识别全部技能 |
| 特殊机制 | 多段施放、充能、刷新、冷却起点特殊的技能须单独定义并验证；未经支持的机制只记录可见事实，不套用普通倒计时 |
| 扩展对象 | 己方技能、召唤师技能和装备主动技能可另行扩展，不作为敌方技能需求完成的替代项 |

开发前还需在支持清单中明确首批英雄 / 技能、游戏版本、画面视角与分辨率、运行硬件，以及各技能的冷却资料来源。文中的验收数字是建议目标，不是已验证能力。

### 4.2 功能要求

#### R1. 自动识别施放事件

系统应识别“某个敌方英雄在某个时刻施放了某个技能”，而不只输出“画面出现技能特效”。每个自动事件必须能关联本局、敌方英雄、技能、采集时间和识别证据。

- 使用连续画面的施法动作、对应技能特效及前后变化进行核对，排除普攻、皮肤特效、己方技能和其他英雄的相似效果。
- 英雄归属、阵营或技能无法确认时，保留为待确认候选；不得创建确定的技能倒计时。
- 低置信或互相冲突的结果不触发到点提醒。置信度阈值须通过实际样本校准，模型自报高置信度不能代替验证。
- 事件时间来自画面采集时间及可靠的局内时间，不能把模型返回时间当作释放时间。推理耗时应从剩余时间中扣除。
- 无法定位到单一时刻时，保留释放时间区间，例如“局内 04:45～04:46”，后续计时沿用该不确定性。
- 同一段持续特效或同一批画面重试只生成一次施放记录；确有新的施放证据时创建新事件。不能因为旧倒计时尚未结束，就一律忽略新的施放。
- 漏掉一次施放后，不能仅凭时间推断敌方“应该已经放过技能”。

#### R2. 记录释放与冷却起点

每次施放记录至少包含：对局、阵营、英雄、技能、释放时间或时间区间、冷却起点、记录来源、识别置信度或人工确认状态、冷却依据、预计就绪时间及当前状态。

“释放时间”和“冷却开始时间”分别记录。普通技能可按已核验规则以施放开始计冷却；若技能在施放结束、第二段施放或其他事件后才进入冷却，必须取得对应事件，不能统一从第一次特效出现开始计时。

人工补录默认表示刚刚施放，也允许填写“已过多少秒”和已知的局内释放时间。只知道剩余时间时，保存登记时刻与剩余秒数，释放时间保持未知。

#### R3. 冷却依据与计算

每个已支持技能须维护适用版本、各技能等级基础冷却、冷却开始条件、冷却缩减规则、是否受特殊刷新或充能影响，以及资料来源和核验日期。

- 技能等级、装备及其他冷却影响因素应来自可核对的画面或人工输入；未知字段保留未知。
- 对普通百分比冷却缩减机制，只有核验该技能适用时，才使用“实际冷却 = 基础冷却 ×（1 − 有效冷却缩减）”。上限、例外和其他计算机制按本局版本处理。
- 如果能确定有效上下界，输出冷却范围；无法取得可靠范围时，不显示精确秒数。
- 支持用户直接填写本次确认的实际冷却，覆盖自动推算；必须标为人工校正并保留原依据。
- 冷却期间发现等级、装备或状态改变时，按已核验规则判断是否影响本次冷却；规则未知则降为待确认，不能随意重算一个确定时间。

计时规则：

| 情况 | 计算与展示 |
| --- | --- |
| 冷却起点和冷却时长均已知 | 预计就绪 = 冷却起点 + 实际冷却；剩余 = max（0，预计就绪 − 当前有效时间） |
| 起点或时长只有区间 | 最早就绪 = 最早起点 + 最短冷却；最晚就绪 = 最晚起点 + 最长冷却；展示剩余范围 |
| 只确认剩余时间 | 预计就绪 = 确认时刻 + 已确认剩余时间；不反推释放时刻 |
| 冷却资料或起点不可靠 | 显示“已记录释放，冷却未知 / 待确认”，不触发确定到期提醒 |

精确倒计时以秒显示，正数向上取整，到期显示状态文字，不显示负数。范围计算应明确仍缺少哪些信息。

#### R4. 时间推进与异常处理

- 计时优先与可靠的局内时间对齐；局内时间暂不可读时，用最近一次可靠的游戏时间与本地经过时间续算，并标为估计。
- 游戏实际暂停、录像暂停时，暂停对应游戏时间的推进；录像倍速影响计时推进，不能始终按现实一秒扣一秒。
- 回放跳转时，恢复该位置对应的有效事件状态；无法恢复时撤下受影响的倒计时，显示待重新观察，不能沿用跳转前的记录。
- 单纯停止视觉识别不等于游戏暂停。已确认的计时记录应保留；画面断流或无法确认游戏是否继续时，展示“观察中断，时间待校准”，暂停新的强到期提醒，恢复后校准。
- 模型处理积压时，过时事件可补入历史，但不能以旧施放时刻重新开启完整冷却。只有时间和后续状态仍有效时才恢复当前计时。
- 页面刷新、浏览器后台节流或设备休眠后，以恢复的有效时间重新计算；不能依靠累计执行了多少次刷新回调来计时。

#### R5. 倒计时与提醒界面

同一对局可以同时显示多名敌方英雄的多个技能。卡片至少包含英雄、技能、剩余时间或范围、状态及来源；展开后可查看释放时间、预计就绪时间、冷却依据和纠错入口。

| 状态 | 示例文案 | 提醒行为 |
| --- | --- | --- |
| 待确认 | “疑似王昭君施放 3 技能，待确认” | 不显示确定倒计时，不弹到期提示 |
| 冷却未知 | “已记录释放，冷却未知” | 提供补录入口 |
| 预计冷却中 | “王昭君 · 凛冬已至 · 预计剩余 25 秒” | 常驻卡片 |
| 即将就绪 | “预计 5 秒后可用” | 最后 5 秒变色，保留文字区别，不只依靠颜色 |
| 进入可能就绪区间 | “可能已可用，最晚预计 5 秒后就绪” | 在最早就绪时轻量提醒一次，明确仍有不确定性 |
| 预计就绪 | “敌方王昭君 · 凛冬已至预计可用，请留意” | 精确到点或到区间最晚边界时，展示醒目文字提醒一次 |
| 已确认可用 | “已确认可用 · 人工确认 / 可读技能状态” | 只有新的直接证据才能进入该状态 |
| 时间失效 / 观察中断 | “时间待校准” | 停止强到期提醒，显示失效原因 |

仅凭倒计时归零，不能把状态改成“已确认可用”。技能计时信息也不能单独触发“现在强开”的战术建议。

提醒规则：

- 到点提示建议持续 5 秒；提示结束后，卡片继续保留“预计可用”状态，直到新施放、纠正、移除或对局结束。
- 同一事件在同一显示端的每个提醒阶段只提醒一次；刷新、重连、重复识别和重复同步不能反复弹出。
- 工作台和大屏各自展示；同一秒内多个技能到点合并为一条提示，卡片分别更新。提示不覆盖当前主战术建议。
- 允许关闭弹出提示，常驻状态继续更新；被撤销或已被新施放替换的事件不再提醒。
- 页面关闭期间不发系统通知；重新打开时恢复最新状态，已结束对局不补发技能提醒，仍在进行的对局可合并提示尚未展示的有效到点事件。

#### R6. 人工补录、纠错与多次施放

用户可以补录、修改或撤销单次记录。修改英雄、技能、释放时间或冷却后，系统重新计算，并同步到所有显示端；历史保留修改前后内容及来源。

- 错认英雄或技能：修正归属，不再保留错误对象的活动倒计时。
- 释放时刻错误：修改时刻或已过秒数，预计就绪时间同步变化。
- 冷却推算错误：录入确认的实际冷却或剩余时间，不必重新虚构一次施放。
- 技能发生刷新：记录刷新依据，结束或修正原计时；没有可靠证据时标为待确认。
- 同一技能再次施放：普通技能以最新有效事件作为活动计时，旧事件进入历史；多段和充能技能按各自规则处理，未经支持时不冒充普通技能计时。
- 人工修正后的同一事件，不应被迟到的旧模型结果覆盖；出现新的独立施放事件时，仍可正常登记。
- 提供单条移除和本局清空；清空活动计时不删除历史，后续新施放仍能自动记录。

#### R7. 对局保存与大屏同步

释放事件、当前状态、纠错历史及提醒去重信息应按对局保存。刷新、短暂断线和服务重启后能够恢复；新建对局不带入上一局的活动计时。

同局大屏应同步新增、修改、撤销、到期状态和对局结束。迟到的旧消息不能覆盖新状态，不同显示端不能各自重新开始一轮完整冷却。

游戏结算经可靠识别或用户确认后结束本局计时，不应要求用户先生成海报才能停止提醒。误判结算可由用户纠正；恢复计时前需重新校准时间和事件有效性。

建议容量：每局最多 40 个活动计时，历史界面默认展示最近 100 条。达到容量时不得静默丢弃既有记录；提示整理已结束记录，并明确新事件是否已进入历史。最终上限可在交互评审中调整。

### 4.3 记录信息要求

以下为业务信息要求，尚不锁定接口、数据库表或字段命名。

| 信息 | 必要性与规则 |
| --- | --- |
| 对局与事件编号 | 必填；一次真实施放对应一个可追踪事件 |
| 阵营、英雄、技能 | 必填；区分已确认归属和候选归属 |
| 释放时间 | 保存采集时间、已知局内时间及必要的上下界；未知不补为 0 |
| 冷却起点 | 明确起点事件与时间；可与释放时间不同 |
| 记录与处理时间 | 用于区分施放发生、画面到达和识别完成，核对延迟 |
| 来源与证据 | 自动识别 / 人工补录 / 人工修正；关联帧编号、证据摘要、模型版本或人工说明 |
| 冷却依据 | 适用版本、技能等级、已知冷却影响、基础值或确认的实际值、资料来源；保留未知项 |
| 预计就绪 | 单一时刻或上下界；保留原始依据与后续修正 |
| 当前状态 | 候选、预计冷却中、可能就绪、预计就绪、已确认可用、待校准、撤销、被新施放替换、对局结束 |

### 4.4 计算与异常示例

以下冷却数字只用于验收计算，不代表任何版本的官方技能数值。

#### 示例 A：自动识别并扣除推理耗时

画面显示敌方王昭君在局内 04:45 施放 3 技能。该技能本次适用冷却已经确认是 30 秒，且规则确认从施放开始计算。识别结果在局内 04:48 返回。

系统自动记下释放时间 04:45、预计就绪 05:15，首次展示约 27 秒倒计时。到 05:10 进入最后 5 秒提示，到 05:15 提醒“预计可用”。不能从识别完成时重新计 30 秒。

#### 示例 B：释放时刻或冷却只知道范围

释放时刻为局内 04:45～04:46，确认冷却范围为 25～30 秒，则预计就绪区间为 05:10～05:16。在 05:10 提醒“可能已可用”，到 05:16 更新为“预计可用”；整个过程不显示“已确认可用”。

#### 示例 C：人工补录与只知道剩余时间

人工确认某技能 5 秒前释放，本次实际冷却为 30 秒，则登记后约剩余 25 秒。若只确认现在还剩 12 秒，则从确认时刻计 12 秒，释放时间仍为未知。

#### 示例 D：画面中断与暂停

技能还剩 20 秒时游戏实际暂停 10 秒，恢复后仍约剩 20 秒。若只是采集断流 10 秒，系统显示“观察中断，时间待校准”；恢复后发现游戏确实继续运行，则校准到约剩 10 秒。两种情况不能混为一谈。

| A02 自动倒计时 | 自动事件具有有效冷却依据 | 自动显示与事件时刻对应的倒计时，扣除识别耗时 |

#### 4.5.2 自动识别质量与性能目标（建议，需在指定环境验收）

- 按首批支持清单逐技能验收，使用人工标注的真实画面，覆盖不同皮肤、遮挡和混战；每个技能至少 50 次施放样本，并加入相似技能、普攻和未施放的负例。开发样本与验收样本分开。
- 事件准确率目标 ≥95%，定义为“正确匹配英雄、技能和同一次施放的事件数 / 系统输出事件总数”；召回率目标 ≥90%，定义为“正确识别事件数 / 支持范围内可见真实施放数”。各技能分别报告，不能只给总体平均值。
- 完全离屏、遮挡导致无法判断的施放不宣称可识别；此类样本数量、未知输出比例和未覆盖技能须单独披露，不能用大量不输出掩盖低覆盖。
- 已输出事件的释放时间误差 P95 目标 ≤1 秒；时间区间输出另报区间覆盖率和宽度，不能用无限放宽区间代替识别准确性。
- 在指定硬件上，施放发生至首次有效提示的端到端延迟 P95 目标 ≤2 秒；超过该目标的技能不宣称具有经验证的即时提醒能力。
- 时间基准有效、页面前台运行时，倒计时显示误差目标 ≤1 秒，到期状态更新延迟目标 ≤1 秒。浏览器休眠恢复应重新校准，而不是补跑遗漏的秒数。
- 冷却计算单独验证版本、等级、缩减和特殊规则；时间计算正确与视觉识别正确分别报告。未知条件输出未知属于正确降级，不能统计为已成功给出准确倒计时。

上述指标未达成前，应继续限制支持清单或标记实验功能。手工录入、模拟模型响应、接口测试和截图演示均不能替代敌方自动施放识别验收。

## 5. 画面采集、模型与状态架构

### 5.1 直接捕获电脑窗口或桌面

首期按 Windows 电脑设计，先支持一个明确的观察目标：指定游戏窗口、某个显示器或该显示器上的区域。目标可为电脑游戏窗口、模拟器窗口，或实际显示游戏画面的浏览器窗口。

| 采集方式 | 适用场景 | 需要验证的条件 |
| --- | --- | --- |
| Windows Graphics Capture 窗口捕获 | 优先隔离指定游戏/模拟器窗口 | 目标应用、窗口模式、遮挡和最小化状态下的实际输出 |
| Desktop Duplication，如 DXcam 封装 | 采集指定显示器，再裁剪游戏区域 | 显示器选择、坐标映射、HDR/色彩格式与全屏模式兼容性 |
| `mss` 截图 | 低频采样原型与兼容性验证 | 实际帧获取速度、画面完整性和 CPU 开销 |

- 先选一条捕获路径跑通并固定依赖版本。OpenCV 用于裁剪、缩放和图像处理，桌面捕获接口由所选采集模块提供。
- 保存观察目标及区域配置；窗口移动、尺寸变化、DPI 缩放或显示器切换时更新坐标，无法可靠定位时暂停该目标的判断。
- 区分“内容没有变化”和“捕获失效”。黑帧、目标关闭、访问失败或可确认的断流应使动态状态过期，暂停新建议。
- 分别验证窗口化、无边框和独占全屏；不支持的模式明确列入兼容性清单，不能静默换成其他应用画面。
- 游戏正常显示与 AI 分析并行运行。建议可放在独立侧栏窗口、另一显示器或大屏；优先使用不包含助教窗口的捕获目标。采用桌面区域捕获时，HUD 应放在采集区域之外，防止建议文字被再次识别为游戏信息。
- 本机直接获取图像时不需要额外的视频编码/解码链路。若推理部署在另一台主机，再单独记录图像压缩和传输开销。

### 5.2 固定模型与推理配置

首轮优先评估 `Qwen/Qwen3-VL-8B-Instruct`，以短输出的状态抽取为目标。推理框架选择一个跑通后固定版本，避免在 vLLM / Ollama 之间同时维护两条未经验证的路径。

原方案记录的 Qwen 官方部署说明推荐 vLLM，并说明 Qwen3-VL 支持需要 `vllm>=0.11.0`；具体模型、量化格式和运行环境仍需验证；本次文档整合未重新核实外部依赖版本。若现有环境为 Windows，vLLM 路线应把适配的 Linux / WSL2 GPU 环境验证纳入排期。若选择 Ollama，则先验证实际版本、模型包、视觉输入和结构化输出支持情况。

必须登记：GPU 型号与显存、驱动、运行环境、模型版本、权重精度、推理框架版本、图像像素预算、同时输入图片数、输出 token 上限、并发路数。

游戏和 Qwen3-VL-8B 在同一台电脑运行时，需要同时测游戏帧率/帧时间、推理耗时和显存占用。先通过裁剪、输出长度与采样频率控制开销；若资源竞争仍影响游戏体验，可把模型放到独立 GPU 或局域网推理主机，屏幕采集仍在游戏电脑上完成。

### 5.3 分阶段识别与调度

- 选人/加载：持续识别槽位、英雄名称、阵营、自身位置、禁用英雄及锁定状态；悬停/预选与正式锁定分别记录，稳定字段复用，画面变化后自动更新。禁选或分路不可读时保留未知，可提供人工纠错入口，但自动视觉链路不依赖逐次人工输入。
- 局中：先做低成本的界面分类和区域变化检测，再按事件需要提取小地图、计时器、血条等区域。Qwen 负责区域语义理解，必要时结合 OCR、模板或专用检测器处理细小数字与图标。
- 结算：待页面稳定后分区域读取；多页数据按对局和玩家槽位合并，未出现的字段留空。
- 全屏低分辨率图可以提供布局上下文；小字区域单独保留清晰裁剪。比较全屏与裁剪组合的准确率、耗时，再决定输入方案。
- 1–2 FPS 仅作为初始抽样配置，不代表能捕捉所有短暂技能、瞬时血量变化和小地图闪现。
- 每路最多保留一个等待处理的最新帧；处理完成后取最新帧，丢弃中间旧帧。分析队列不得无限积压。

减少外部文本 API 调用只能降低一部分成本。连续视觉推理仍可能是主要算力瓶颈，应同时测量单路 GPU 占用和多人并发容量。

### 5.4 结构化状态与跨帧记忆

不要只把视觉 JSON 直接送给战术模型。增加可校验、可过期、可追溯的状态层。

| 状态字段 | 要求 |
| --- | --- |
| `session_id`、`frame_id`、`state_version` | 区分对局、证据帧和状态版本，防止旧请求污染新对局。 |
| `captured_at`、`received_at`、`processed_at` | 记录画面采集、服务接收及识别完成时间；能取得源时间戳时做时钟映射。 |
| `phase`、`game_time_s` | 阶段区分选人、加载、对局、结束动画、结算、未知；计时器不可见时不得填 0。 |
| `player_context` | 明确在辅助谁、队伍方向、操控英雄/分路，避免给错阵营的建议。 |
| `lane_context` | 记录我方英雄、敌方实际对位、所在路线及对位确认状态；记录可见等级、血量/资源、装备、兵线位置与数量、塔距、支援威胁和技能事件证据。缺失字段保留未知并分别设置有效期。 |
| `bp_context` | 记录禁选/选人阶段、双方已锁与预选英雄、禁用列表、是否轮到用户、用户是否已锁定、可读的剩余时间；未读到的字段标为未知。 |
| `player_preferences` | 可选的擅长英雄和可用英雄池，仅用于个性化排序，不是启动实时判断的前提；当前分路优先从可靠画面识别，必要时允许纠正。无法从画面确认的熟练度等信息不猜测。 |
| `observations` | 每个字段记录值、观测范围、来源帧、证据区域和最近确认时间。 |
| `source` | 区分 `observed`（直接读到）、`derived`（按规则计算）、`unknown`（不可知）。 |
| `valid_until` | 动态状态设置过期时间；不同字段分别设置有效期。 |

关键约束：

1. 未知用 `null` / `unknown`，不以 0、死亡、目标不存在代替未识别到。
2. 英雄、血量范围、时间和阵营做枚举/范围校验；非法 JSON 或字段冲突不得进入事件判断。
3. 模型自报置信度仅作为线索，不能直接当作经过校准的正确概率。结合清晰度、字段一致性和标注集结果决定是否采用。
4. 趋势来自带时间戳的连续状态；连续帧一致只是过滤抖动的方法，不能证明识别一定正确。
5. “小地图当前可见敌方 2 人”“敌方当前存活 2 人”“目标区域敌方 2 人”是三种不同信息，不得互相替代。
6. 敌方失去视野后只保留带时间的最后观测位置，过期后标为未知。
7. 目标倒计时优先读可见 UI；规则推算需要当前版本规则及可靠的前置事件，并标明推算来源。不能只凭对局时间反复套固定刷新周期。

识别提示词应限定：只提取指定字段，附来源，无法判断时留空。屏幕内聊天、昵称和其他文字作为被观察的数据，不能覆盖识别与战术服务的指令。

### 5.5 事件触发、建议有效期与降级

建议链路：

```text
电脑游戏窗口 / 指定显示器区域（游戏正常显示）
                  ↓ 桌面或窗口捕获，获取最新帧
         阶段识别 + 按需区域裁剪
                  ↓
       Qwen3-VL-8B / 必要的 OCR 或检测器
                  ↓
       字段校验 → 跨帧状态 → 事件判断
                  ↓
       按阶段处理：BP 候选筛选 / 局中事件规则
                  ↓
       按英雄、对位和事件查询已核验战术事实
                  ↓
     简单确定事件：本地模板；候选解释/复杂建议：外部 API
                  ↓
       候选与依据校验 + 过期检查 + 去重
                  ↓
      WebSocket → 电脑侧栏 / 副屏 / 大屏 HUD
```

每类事件必须定义：前置条件、必要证据、连续确认窗口、触发阈值、冷却时间、优先级、失效条件和可用模板。

以上链路随视频采样持续运行。建议发出后仍检查最新视觉状态；无需等待下一次 API 返回或用户操作才撤销失效卡片。界面阶段由视觉状态机自动切换，阶段不确定时保留未知并暂停依赖该阶段的新建议。

例：识别到目标倒计时进入预告窗口后，经连续观测确认且本轮尚未提醒，触发一条准备目标的提示。若倒计时不可读或规则版本未确认，则不触发确定时间的建议。

- 防抖初值可采用连续 2–3 次观测或一个短时间窗口，最终按事件速度和误报表现调整；这会增加延迟，须计入预算。
- 相同事件去重，并采用进入/退出不同阈值，减少在边界反复提示。
- API 请求绑定 `session_id`、事件编号、来源状态版本、依据时间及有效期。返回后重新检查必要状态；过期、事件取消、阶段变化或对局结束时丢弃。
- HUD 到期自动撤下，断线重连不重放过期提示。断流时撤下依赖动态状态的战术卡片。技能释放记录与历史按第 4 章保留，时间失效时显示待校准并停止强到期提醒，不因停止视觉观察而删除记录。
- API 超时、限流或不可用时，只有依据仍有效才用本地模板，否则跳过；局中不反复重试旧事件。
- 设定每分钟请求上限、同类事件冷却、每局费用上限及并发限制；取消与当前局面无关的等待请求。
- 提示长度建议：局中行动句约 15–30 个汉字，按需补一行依据；赛前约 60–100 字；赛后约 120–150 字。

## 6. 知识库与教练规则

### 6.1 资料结构、审核与检索

首期采用 JSON / SQLite 等结构化资料，按英雄 ID、对位、分路和事件类型查询。先维护已审核的英雄和关系子集；无需新增向量数据库或长文档切片检索服务。后续资料规模扩大后再评估检索方案。

| 资料类型 | 最少内容 |
| --- | --- |
| 英雄资料 | ID、名称/别名、适用分路、职责标签、关键机制、使用条件 |
| 对线关系 | 我方英雄、敌方同路英雄、分路、等级/装备阶段、清线/换血等维度、优势与失效条件、资料来源与版本 |
| 全局战术关系 | 阵容搭配与团战限制单独存储，仅用于对应扩展功能，不能混入对线排序 |
| 战术与出装要点 | 分路、游戏阶段、行动建议、必要前提；具体装备建议附适用版本 |
| 来源与审核 | 游戏版本、资料来源、核验日期、审核状态；未核验或失效条目不用于确定性推荐 |
| 事件模板 | 触发条件、必要事实、行动句、失效条件和优先级 |

附录 A 及现有英雄资料作为待审核素材，不能仅因已有“60+ 英雄”条目就视作当前版本验证通过。BP 功能首期验收同时提交覆盖英雄、关系数量和未覆盖场景清单。

向外部 API 提供当前已确认状态、合格候选、命中的已核验事实、短事件历史和未知项，要求返回建议及依据 ID。服务端校验候选范围、响应结构、依据是否存在与是否过期。只告诉模型当前版本不能让它自动获得该版本知识；不允许模型自行补全缺失的克制关系或装备数值。

### 6.2 教练判断与表达

教练建议应先识别获胜条件，再把它转换为当前能执行的动作、时间点、对象和目的。分析阵容时考虑：谁负责前排与开团、谁在前期具备条件优势、谁是后期核心、敌方主要威胁以及己方最需要弥补的短板。

局中优先处理迫近风险和已失效建议，再考虑短时间有效的团战 / 资源准备、对线和一般解释；旧知识库中“目标永远优先于安全”的固定顺序不再采用。界面只保留一条主建议和一个有依据的备用动作。

参考阶段规划可按 0～2 分钟观察一级入侵与视野、2～4 分钟关注已确认资源和中路线权、4～8 分钟争取塔与资源转化、8～12 分钟结合装备和边线组织、12 分钟后重视关键目标与高地视野。该时间轴是训练思路，**不能直接作为本局资源刷新时间或英雄强势期的证据**，实际执行需核对版本与当前局面。

BP 说明约 60～100 字，加载摘要约 60～100 字并允许展开，局中主句约 15～30 字并按需补一行依据，赛后约 120～150 字。语气直接、尊重玩家；指出问题时给下一次可执行的替代动作，不用贬损标签。


### 6.3 阵容与对局模板

#### 6.3.1 己方有强开团

目标：利用视野和先手迫使敌方交位移，再用第二轮技能收割。

执行顺序：清中线 → 抢入口视野 → 等核心到位 → 先手控制关键目标 → 立刻转塔或中立资源。

避免：开团后只追残血，导致敌方复活或支援后反打。

#### 6.3.2 己方偏后期

目标：用清线和视野换装备时间，不在前期无条件接团。

执行顺序：保护发育核心 → 放弃不可守的小资源 → 用边线牵制 → 在关键装备后抱团争主目标。

避免：为了守没有兵线优势的外塔，把核心交给敌方强势期。

#### 6.3.3 己方边带强

目标：让边带制造人数选择题，而不是五人抱团浪费单带能力。

执行顺序：边线推过河道 → 其余四人控制中线和视野 → 观察敌方分人 → 选择转塔、入侵或逼主目标。

避免：单带英雄无视野压深，或四人提前露出位置让对手轻松抓边。

#### 6.3.4 己方落后

目标：减少正面随机团，通过清线、换资源和抓脱节逐步恢复经济。

执行顺序：抱团清危险线 → 守高价值入口 → 只接人数或技能优势团 → 把一次击杀转换成塔/野区/主目标。

避免：连续单人探草、抢没有惩击优势的资源、多人追入敌方复活区。

### 6.4 维护与覆盖口径

- 现有机制知识库包含 60 位唯一英雄：对抗路 12、中路 13、发育路 10、打野 13、辅助 12；另有 10 条通用决策。完整英雄条目见附录 A。
- 机制知识与技能冷却资料分开维护。英雄存在于知识库，只表示收录了资料，不代表数值、对位关系、皮肤适配或自动识别已通过当前版本验收。
- 每赛季复核定位、装备和标签，大版本更新后重新抽查克制、强度与数值；记录版本、资料来源、核验日期和审核人，失效内容标为待复核。
- 先覆盖高频英雄和高频事件，再扩大范围。无审核依据时解释一般机制或保留未知，不给绝对克制胜率、虚构排名或未经验证的装备结论。
- 当前代码数据入口包括 `resources/knowledge/hero_relations.json`、`resources/knowledge/knowledge_base.json` 和 `resources/knowledge/skill_catalog.json`；整合文档用于需求与资料查阅，不自动替代这些运行数据文件。

## 7. 赛后复盘、海报与分享

流程调整为：识别结束阶段 → 等待结算页可见且稳定 → 提取当前可见字段 → 校验/合并 → 生成数据摘要 → 合成海报和二维码。

- 若用户未进入详细战绩页，生成当前可见数据的简版结果；不得声称完整取得十人战绩。
- 参团率只能由可靠的个人击杀、助攻和队伍总击杀等必要字段，按确认口径计算；分母为 0 时标为不适用。
- “经济转化”等指标必须定义公式并确认数据足够，否则移除。
- 官方 MVP 仅在界面明确显示时提取；模型生成的表现点评应与官方评定分开。
- 只有结算截图：写数据摘要与改进建议，不声称还原了关键团战或整局胜负原因。
- 有局中事件日志：引用具体时间和事件，明确未覆盖的阶段。事件日志至少保留事件时间、证据帧引用、已确认状态、建议、展示时间及可观察结果。
- “系统发出建议”不等于“用户执行建议”；没有可靠后续证据时不评价执行情况。
- 有合格行为记录时，战报加入一条具体回顾和下一局训练目标；无过程证据时只输出数据点评与通用练习。趣味评语围绕游戏行为，避免无依据地指定“背锅位”。
- 海报与二维码需校验访问地址是否能被手机访问，并说明访问有效期。

### 8.3 整屏采样与加载打法方案（2026-09-09）

用户已选择监控整块屏幕。Windows 本机可列出显示器，选择后手动启动一次；每次推理结束后重新采集最新画面，等待间隔可选 1 / 2 / 5 秒，不积压视频帧。可暂停、停止，源切换和旧请求取消有状态保护。当前循环由前端驱动，关闭页面即停止，后台浏览器节流可能影响频率。样本最长缩放至 1280×720，自动观察不留图；手机等远程访问不能调用本机屏幕接口。

加载阶段新增「这局怎么打」面板及右侧「这局先记住」卡片：

1. 展示开局分路与资源分工、团战进场与保护、优势转塔或目标、劣势守线，以及针对敌方机制的重点防范。
2. 能切换方案方，选择一位已列入该方的英雄查看个人任务。查看哪一方不等于确认用户所属阵营，不从卡片位置猜用户英雄。
3. 网上样本上下排阵容由助手核对，明确标注来源。样本只作方案预览，不写入真实对局的阵容、技能事件或建议记录。
4. 视觉观察返回加载阶段与双方英雄时自动生成阵容草稿方案；识别失败、不含双方英雄时不伪造阵容。当前接入层没有可靠英雄置信度，因此草稿需核对，不宣称敌我身份确认或实时战术已验证。
5. 可编辑英雄名。编辑、切换阵营或画面来源后撤下旧建议，取消旧请求；人工纠正不会被后续同一观察会话的识别候选覆盖。重复阵容不重复请求。
6. 基础建议使用本地机制规则，无需调用付费文本接口；补充妲己与米莱狄的定性机制草案。具体版本、装备数值、技能冷却、胜率、当前隐藏位置都不从静态阵容推出。

已验证：4 项新增 Python 用例（双向打法差异、个人任务、未覆盖英雄、接口非法输入）和 5 项界面状态用例（切换、纠错、取消、视觉候选生命周期、人工修正优先）；原技能计时与整屏监控相关用例通过。真实浏览器载入网上样本、切换上下排、选择蔡文姬、非法阵容提示、停止撤下方案及 390px 视口横向溢出检查通过；页面截图已保存到用户指定文件夹。

后续进展：已经兼容 Ollama 把完整结构化 JSON 放入 thinking 字段的行为；仅接收正常终止的完整 JSON，不从思考段落中提取片段，截断结果仍丢弃。补充加载画面的判别说明后，样本能返回 loading，但英雄身份与阵容顺序仍有误认。真实英雄识别准确率尚未通过验收；敌方施放时间与技能倒计时自动识别仍按第 4 章另行实施。

### 8.4 进入页面后自动观察、外部分析与摘要（2026-09-09）

用户确认复用 DeepSeek，并提供本机接口配置。已核验服务的模型清单，接入 `deepseek-v4-flash`，真实完成 Qwen3-VL → DeepSeek V4 → 页面建议的样本联调。

**进入与停止：** 普通工作台默认读取已选择的本机显示器，先检查 Ollama 再自动开始持续观察。用户可关闭自动启动偏好、暂停或停止；不因晚到响应而恢复采集。`sample=loading` 使用样本图片自动调用一次 Qwen3-VL，保持明确的示例标记，不自动采集桌面。大屏模式与 `monitor=off` 只展示内容。

**分析内容：** 由视觉结果生成白名单事实，包括游戏阶段、两组已读英雄、可靠可见的操控英雄与必要状态；加载阵容只是屏幕组别，不能擅自确定用户阵营。用户选择分析方/英雄后围绕该方讲打法；用户未选择且无法可靠确认时使用双方视角。网络样本或人工核对阵容单独标注，不冒充自动识别。

DeepSeek 基于事实与定性机制资料分析阵容获胜条件、主要风险、争取优势的方式，并返回一段约 80～180 字的行动建议；展开区域可看注意事项与优势机会。外部模型可做有条件的战术分析，不再仅限于润色本地模板，但不能补猜敌方技能、隐藏位置、经济差、版本数值或胜率。摘要应只围绕选中方，不同时给对手下指令。

**调用与时效：** 每局两次外部分析至少相隔 20 秒；同一事实与视角的阵容分析复用最多 120 秒，连续画面只保留最新待分析内容，不建立逐帧队列。局内时间分钟段、血线档位、阵容、阶段或视角变化会形成新的分析条件。实时可见状态需在采样 12 秒内仍有效，返回超时则撤下；较旧画面只给明确标注的阵容建议，移除动态血量/技能事实。180 秒以上的旧观察不再用于新分析。

**故障与数据：** 此文本链路的 DeepSeek 请求超时为 25 秒。未配置密钥、请求失败、输出结构不合规、引用不存在依据或补出阵容外英雄时显示本地备用建议，并清楚标注来源。本节文本接口只接收白名单游戏事实与机制资料，不接收截图、视频、昵称、聊天或视觉自由文本；后续 8.7 的图片多模态链路按用户授权发送所选区域，两者范围不同。密钥只在服务端本机 `.env` 中读取，不返回浏览器或分析记录。配置变化可通过页面重试入口生效，无需重启。

**验证与限制：** 此阶段新增 12 项后端用例与 7 项界面用例覆盖解析兼容、隐私字段过滤、缓存、节流、过期、未知阵营、取消、纠错、自动启动、展示模式隔离及摘要视角筛选。真实样本调用获得 `deepseek-v4-flash` 正常响应，并保存显示结果；这次外部分析使用明确标注的样本核对阵容。如果模型把双方指令混在摘要中，应用从该次模型返回的注意事项和机会中筛选当前方内容，并补充通用执行条件与转资源要求，页面标明经过整理；无法筛选则回退，不混用两方指令。此前 CPU 环境中新样本推理约 36～42 秒，相同图片缓存命中约 15 秒；后续 GPU 修复及英雄优先模式实测见 8.5。当前仍不承诺瞬时战斗指挥或自动施放识别质量。

### 8.8 英雄误认修复要求（2026-09-10）

用户指出测试截图的英雄名错误。核对发现，V4 接口测试只按返回模型名记为成功，实际测试图十个英雄均不匹配。必须将“调用成功”和“识别正确”分别记录。现有英雄库枚举只能约束名字合法，不能证明名字出现在画面中。

修复优先按图片中英雄名称的文字、位置和置信度提取证据；皮肤名称与玩家昵称不能直接作为英雄名。自动阵容只采纳有可靠文字证据的英雄，缺失槽位保持未知。外部 V4 负责基于证据生成打法，不能另造阵容；本地识别失败时不得直接用外部猜测补满阵容。已知样本名单仅用于测试比对，不能写进识别规则或模型提示伪装识别成功。低清图不允许以猜满名单作为验收通过。

### 9.4 整体系统验收

验收至少包含：

1. **识别质量**：按游戏阶段和字段统计准确率、可用覆盖率、错误接受率；英雄分别报告单槽位和完整阵容全对率。拒绝所有结果不能算达标。
2. **事件质量**：人工标注事件，统计精确率、召回率、每小时误报数、重复卡片数和过期卡片数；分别报告各类事件。
3. **数据划分**：按完整对局划分调优集和测试集，避免相邻画面跨集合导致成绩虚高；覆盖皮肤、特效、遮挡和界面变化。
4. **延迟**：报告 P50/P95，并注明设备、分辨率、实际输入像素、输出长度和并发。记录从证据画面采集到 HUD 实际显示的时间，另测真实事件发生到提示的时间，计入抽样和连续确认等待。
5. **目标性质**：原文 300–600ms 视觉、2 秒建议、5 秒战报可保留为待验证优化目标；第一周压测后确定可验收数值。战报计时从完整结算页稳定可见开始。
6. **稳定与降级**：测试目标窗口关闭/最小化、切换全屏、DPI/分辨率变化、多显示器、捕获黑帧/中断、模型异常、API 超时/限流、JSON 非法和跨局重置；可先以连续 2 小时或 5 局作为 Demo 测试起点，记录实际完成量。
7. **用户效果**：记录提示是否来得及执行、是否打扰、是否易读和游戏使用者对建议的评价；不能用未经对照的胜率变化证明有效。
8. **成本与容量**：记录单局 API 次数/费用、视觉推理占用和多路竞争情况；同机部署时比较开启/关闭助教前后的游戏帧率与帧时间波动，并事先约定可接受影响。单路通过后再确定每台推理主机支持的席位数。
9. **BP 候选资格**：在已确认状态的测试用例中，不出现被禁用、按当前模式被占用、已知不可用或分路不适用的候选；用户锁定后不继续推荐换英雄。覆盖禁选变化、预选更换、用户锁定、候选不足和字段未知等场景。
10. **对线判断质量**：候选解释关联到有效的同路对位资料；评审清线、换血和等级/装备阶段是否适用，统计对位资料覆盖率与无合格候选比例。测试换线、对位未知、血量劣势、兵线改变和支援出现后能否调整或撤销压制判断；不以阵容评价、团战表现、全局胜率或模型自评分作为替代指标。
11. **行为回顾真实性**：未知轨迹、时间窗外行为和缺失结果均保留未知；人工补录或演示样本明确标注。首期若未上线自动追踪，不将人工演示计为自动识别通过。
12. **实时视觉闭环**：选定电脑窗口或区域并启动监测后，自动完成画面采样、阶段识别、BP 更新、已支持事件判断、卡片失效与结算触发。记录实际有效观测频率、状态新鲜度和事件到提示/撤销的延迟。必须包含直接观察电脑游戏画面的验收；手动截图、人工录入状态或点击模拟事件的演示不能替代该项。
13. **团战与互动**：分别检查队友未到、技能未知、前排阵亡、局部人数变化和团后兵线等场景；能区分准备、拉扯、撤退与转资源。切换风格不改变事实和行动结论；主动提示关闭与暂停观察具有不同效果；问答不返回过期战术。

采集到提示显示的延迟可以分解为：电脑画面捕获 + 裁剪/预处理 + 排队 + 视觉推理 + 状态/事件处理 + API + 传输渲染。异机推理额外计入图像编码与传输。真实事件到提示还要考虑抽样等待与连续确认。WebSocket 只解决最后的传输步骤。

技能识别质量和计时精度另执行第 4.5 节。原方案所述 1～2 FPS、事件期 3～5 FPS、建议 8～15 秒有效期是待按事件校准的配置建议，不保证覆盖瞬时技能；当前演示规则的固定参数列于附录 B。

### A.1 英雄战术条目（60 位）

> 共 60 个不重复英雄：对抗路 12、中路 13、发育路 10、打野 13、辅助 12。分路为常用位置，不是强制分路。

#### A.1.1 亚瑟

- 常用分路 / 定位：对抗路 / 战士/坦克。
- 机制威胁：沉默突进和近身追击。

- 己方使用 / 配合：用沉默限制进场者，清线后协防中路。
- 前期节奏：控安全兵线，留意敌方打野位置。
- 中期节奏：清边后协防，别为追人丢塔。
- 后期节奏：边线与主目标同步施压，保留退路。

#### A.1.2 白起

- 常用分路 / 定位：对抗路 / 坦克。
- 机制威胁：嘲讽开团和持续承伤。
- 常见弱点：依赖进场距离，怕减回复和拉扯。
- 对阵时 · 对线应对：利用清线空窗换血，不在兵堆里久战。

### B.2 现有演示路径（用于区分现状与目标）

1. **赛前战术**：点「载入示例阵容」后生成方案；也可点 10 个位置逐个选择。每队最多 5 人，不允许重复。
2. **同步大屏**：打开右上角「打开同步大屏」，同一对局实时推送；刷新后恢复已保存的阵容与未过期建议。大屏只同步战术，素材画面需在大屏本机打开 / 共享。
3. **局中观察**：点「目标将刷新」「人数劣势」「关键英雄消失」「安全换资源」等示例，确认后评估。示例有明确标记，不是真实对局观察。未知人数 / 技能不能触发强开建议。
4. **执行记录**：选择建议，输入可观察动作、局内秒数、置信度和结果。建议在 285 秒发出则 285~297 秒是观察有效窗口；超时观察标为不确定，而非没有执行。
5. **赛后复盘**：手填胜负、英雄、KDA 及已知资源数据，生成 PNG、二维码与 H5。空值不补成 0，不编造 MVP、伤害和胜负原因。
6. **英雄知识库**：支持英雄 / 机制 / 分路检索，以及 60 个完整条目浏览。
7. **技能计时预研（未完成新增需求验收）**：现有人工登记入口可用于检查记录、倒计时和提示。目标流程是敌方施放后自动识别并计时，完整目标见第 4 章。

### B.3 现有画面输入

- 上传 PNG/JPEG/WebP 截图（8MB 内），或播放本地浏览器支持的录屏视频，暂停后分析当前帧。
- 本机打开 scrcpy / OBS 预览，再点「共享投屏窗口」选择该窗口；不采集麦克风和摄像头。
- scrcpy 需安卓手机、USB 数据线与手机端 USB 调试确认；这部分没有现场设备，未测 50ms 时延。
- 图像可按归一化 x/y/宽/高裁切。ROI API 实际裁切，不仅改变显示；上传原文件与用于模型的裁切 JPEG 均留存。
- 支持人工触发截帧，也可手动开启连续观察，读取阶段、操控英雄、血量及自身可见技能倒计时；敌方技能释放仍由人工确认登记。视觉草稿必须人工核对后提交。
- 浏览器屏幕共享需要 localhost 或 HTTPS，局域网 HTTP 通常不支持共享；手机只看战报不受影响。

### B.4 可选模型配置

把 `.env.example` 复制为 `.env`，仅在本机填写配置；不要提交密钥。
`start.ps1` 会自动传入 `--env-file .env`；直接运行 uvicorn 时也需显式加这个参数。

#### B.4.1 Ollama 视觉

安装 Ollama 和适配硬件的视觉模型，例如：

```powershell
ollama pull qwen3-vl:8b
ollama serve
```

若 Ollama 桌面服务已运行则不必重复 serve。默认地址 `http://127.0.0.1:11434`，可用 `OLLAMA_URL` / `OLLAMA_VISION_MODEL` 修改。
BP、局面和结算均输出结构化草稿；看不清时保持未知，低于 0.8 不给具体 BP 推荐。超时后显示可理解错误并允许手动兜底；具体超时值应按当前运行配置核对。
模型安装及可用状态以现场检查为准；没有目标游戏画面的实测结果时，不宣称达到 95% 识别率。

#### B.4.2 DeepSeek 文本层

原工作台「AI 对局建议」文本链路使用 `deepseek-v4-flash`，25 秒请求超时，对有效游戏事实分析风险与优势机会，只发送白名单结构化游戏信息与机制资料，不发送截图、视频和自由 OCR 文本。新的固定区域图片分析见 8.7，使用单独的视觉模型配置和所选图片外发授权。
原规则润色接口继续保留 2 秒超时与规则优先策略；它与新分析链路是不同入口。API Key 在本机服务端读取，不返回浏览器、不写入分析记录；配置方法与时效策略见第 8.4 节。

### B.5 局域网与分享地址

默认仅监听本机。手机观看战报需使用 `start.ps1 -Lan`，电脑和手机处于同一可信局域网；防火墙和访客 Wi-Fi 隔离须现场检查。浏览器屏幕共享通常要求 localhost 或 HTTPS，局域网 HTTP 不一定可共享。

使用 `PUBLIC_BASE_URL=http://电脑局域网IP:端口` 配置扫码站点，换网络或端口后重新核对地址、重启并生成新战报。旧 README 记录本机曾使用 `http://192.168.0.46:8765`；该地址是历史环境示例，不保证当前有效。

二维码指向本机 H5，不上传第三方平台，也不依赖外部 CDN、在线二维码或外部字体。随机战报 ID 不提供账户鉴权；不要把当前可信局域网演示直接暴露公网。
