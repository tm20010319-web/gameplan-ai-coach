# 小象助手：语音记录敌方技能与冷却倒计时方案

版本：v0.1  
日期：2026-09-23  
状态：方案设计稿

## 1. 目标

为电脑端配合模拟器或投屏使用的《王者荣耀》辅助工具增加语音交互能力。

用户看到敌方英雄释放大招或闪现后，只需要说出类似下面的指令：

- “小象助手，妲己放大了”
- “小象助手，孙悟空闪现了”

系统即可：

1. 识别唤醒词和技能事件；
2. 从知识库读取默认冷却时间；
3. 创建敌方技能冷却倒计时；
4. 在屏幕悬浮层显示倒计时；
5. 使用语音确认已记录的事件；
6. 在技能预计转好时进行一次轻量语音提醒。

本工具面向个人排位和娱乐局使用，不要求开局手动配置敌方阵容，也不依赖游戏画面自动识别。

## 2. 已确认的使用边界

| 项目 | 确认内容 |
| --- | --- |
| 使用环境 | 电脑端配合模拟器或投屏 |
| 信息输入 | 用户通过语音报告技能释放 |
| 唤醒词 | “小象助手” |
| 语音指令 | “某某英雄放大了”“某某英雄闪现了” |
| 输出方式 | 屏幕悬浮层显示，同时语音播报 |
| 计算对象 | 敌方英雄大招和闪现 |
| 阵容配置 | 不要求用户开局配置，直接按语音中的英雄名处理 |
| 未知参数 | 等级、装备、冷却缩减未知时使用知识库默认值 |
| 网络条件 | 个人使用，可联网调用语音服务 |
| 视觉识别 | 不作为本方案的必要条件 |
| 游戏操作 | 不读取游戏内存、不注入游戏、不自动点击或释放技能 |

## 3. 总体架构

```text
麦克风
  ↓
唤醒词检测：“小象助手”
  ↓
语音活动检测（VAD）
  ↓
语音识别（ASR）
  ↓
指令解析与英雄名称匹配
  ↓
技能事件服务
  ↓
知识库查询 + 冷却计算
  ↓
对局计时状态（SQLite）
  ├─ 屏幕悬浮层
  └─ 语音反馈与到期提醒
```

建议把语音识别服务设计为可替换适配器。第一版可以使用联网语音识别，后续仍可替换为本地识别，不影响计时和悬浮层逻辑。

## 4. 语音交互设计

### 4.1 唤醒流程

系统持续监听麦克风，但只有检测到“小象助手”后才接收后续指令。

示例：

```text
用户：小象助手，妲己放大了
系统：已记录妲己大招，开始倒计时
```

不建议让系统在没有唤醒词时持续解析全部语音，以减少误触发和游戏语音干扰。

### 4.2 第一版支持的指令

| 用户表达 | 解析结果 |
| --- | --- |
| “妲己放大了” | 英雄：妲己；技能：大招 |
| “妲己开大了” | 英雄：妲己；技能：大招 |
| “妲己大招” | 英雄：妲己；技能：大招 |
| “孙悟空闪现了” | 英雄：孙悟空；技能：闪现 |
| “孙悟空交闪了” | 英雄：孙悟空；技能：闪现 |

### 4.3 识别失败处理

如果没有识别出英雄名称，系统不应创建倒计时，而应提示：

> 没有听清英雄名称，请再说一次。

如果英雄名称匹配存在多个候选，应在悬浮层显示待确认状态，并通过语音请求确认。

## 5. 指令解析策略

第一版采用规则解析，不把大模型放在计时关键路径上。

### 5.1 技能意图

```text
“放大了”“开大了”“大招” → ultimate_cast
“闪现了”“交闪了” → flash_cast
```

### 5.2 英雄名称匹配

英雄名称应从知识库生成匹配表，并支持：

- 官方名称；
- 常用简称；
- 用户自定义别名；
- 同音字和常见语音识别错误；
- 轻微的模糊匹配。

例如，“猴子”可映射为“孙悟空”。

### 5.3 事件结构

每次成功解析后生成一个技能事件：

```json
{
  "hero": "妲己",
  "skill_type": "ultimate",
  "source": "voice",
  "recognized_text": "妲己放大了",
  "recorded_at": "2026-09-23T14:30:00+08:00",
  "cooldown_source": "skill_catalog",
  "status": "cooling"
}
```

## 6. 冷却计算规则

### 6.1 知识库来源

现有项目中的相关资料包括：

- [`resources/knowledge/skill_catalog.json`](../../resources/knowledge/skill_catalog.json)：英雄技能和基础冷却；
- [`resources/knowledge/summoner_skills.json`](../../resources/knowledge/summoner_skills.json)：召唤师技能，包含闪现基础冷却；
- [`resources/knowledge/voice_assistant_knowledge.json`](../../resources/knowledge/voice_assistant_knowledge.json)：为“小象助手”生成的全量语音计时知识库，当前覆盖 132 名英雄；
- [`gameplan/skills/cooldowns.py`](../../gameplan/skills/cooldowns.py)：现有冷却计算逻辑；
- [`gameplan/monitoring/overlay.py`](../../gameplan/monitoring/overlay.py)：现有悬浮层相关逻辑。

全量语音知识库由 [`scripts/build_voice_knowledge.py`](../../scripts/build_voice_knowledge.py) 从原始技能资料生成。生成结果包含英雄 ID、标准名称和初始匹配别名、大招名称、按技能等级的基础冷却、默认冷却、冷却范围、特殊机制标记、冷却说明和资料来源；同时包含闪现的默认基础冷却。后续可在 `aliases` 字段中继续补充“猴子”等常用口语别名。

当前原始官网资料没有明确标注正式服版本，因此知识库保留采集时间和来源，并把动态冷却、无固定冷却和需要复核的技能标记出来。对于这些技能，助手应记录释放事件，但不强行显示精确倒计时。

### 6.2 默认计算

- 大招：查询对应英雄大招基础冷却；
- 闪现：查询召唤师技能“闪现”的基础冷却；
- 等级、装备、铭文和冷却缩减未知时，使用知识库默认值；
- 找不到可靠冷却数据时，显示“冷却未知”，不伪造精确倒计时。

### 6.3 冷却起点

第一版以语音事件的有效记录时间作为冷却起点。由于用户通常是在看到释放后才开始说话，该时间代表“用户报时点”，并非游戏内真实施放时刻，界面应使用“预计”字样。

后续可以支持：

- “妲己刚才放大了”；
- “妲己 5 秒前放大了”；
- 快捷键对倒计时进行加减；
- 语音修正本次事件的已过时间。

## 7. 悬浮层设计

悬浮层应满足：

- 置顶显示；
- 可拖动；
- 可调整透明度；
- 不抢夺游戏焦点；
- 不遮挡主要操作区域；
- 支持同时展示多个英雄的多个技能。

单个计时卡片建议显示：

```text
妲己
大招
预计剩余 18 秒
```

多技能示例：

```text
妲己       大招       18 秒
孙悟空     闪现       42 秒
王昭君     大招        7 秒
```

### 7.1 状态

| 状态 | 展示文案 |
| --- | --- |
| 冷却中 | “预计剩余 18 秒” |
| 即将转好 | “预计 5 秒后可用” |
| 预计可用 | “预计已转好” |
| 数据未知 | “已记录释放，冷却未知” |
| 待确认 | “疑似某英雄施放，待确认” |

倒计时归零后卡片不立即删除，保留“预计可用”状态，直到发生新的施放、用户撤销或对局结束。

## 8. 语音反馈设计

语音只播报关键状态，不逐秒播报，以免影响游戏操作。

### 8.1 成功记录

```text
已记录妲己大招，开始倒计时。
已记录孙悟空闪现，开始倒计时。
```

### 8.2 识别失败

```text
没有听清英雄名称，请再说一次。
没有找到这个英雄的冷却数据。
```

### 8.3 到期提醒

```text
妲己大招预计 5 秒后转好。
妲己大招预计已转好。
```

同一事件的确认和到期提醒各播报一次，避免重复打扰。

## 9. 数据保存

每场游戏建立独立的计时会话，建议保存以下字段：

| 字段 | 说明 |
| --- | --- |
| session_id | 对局编号 |
| event_id | 技能事件编号 |
| hero | 英雄名称 |
| skill_type | 大招或闪现 |
| recorded_at | 语音记录时间 |
| cooldown_seconds | 使用的冷却秒数 |
| ready_at | 预计转好时间 |
| source | voice |
| recognized_text | 原始识别文本 |
| status | 冷却中、预计可用、撤销等 |
| created_at | 事件创建时间 |

计时应基于绝对时间或单调时钟重新计算，不能依赖定时器回调执行次数。程序重启或悬浮层刷新后，应从保存状态恢复剩余时间。

## 10. 推荐实现顺序

### 阶段一：最小可用版本

- 接入唤醒词“小象助手”；
- 接入普通话语音识别；
- 支持“某英雄放大了”；
- 支持“某英雄闪现了”；
- 查询现有知识库；
- 创建单个或多个倒计时；
- 悬浮层显示；
- 语音确认。

### 阶段二：稳定性增强

- 英雄别名和同音纠错；
- 多个计时同时运行；
- SQLite 对局保存和恢复；
- 冷却结束提醒；
- 快捷键暂停、清空和撤销；
- 网络或语音服务短暂失败后的重试。

### 阶段三：高级交互

- 支持“几秒前”时间表达；
- 支持语音纠错，例如“不是妲己，是小乔”；
- 支持自定义实际冷却；
- 支持查询“某英雄还有多久”；
- 支持一局结束后的技能记录统计。

## 11. 验收标准

第一版至少应满足：

1. 说出“小象助手，英雄放大了”后，能够正确创建大招倒计时；
2. 说出“小象助手，英雄闪现了”后，能够正确创建闪现倒计时；
3. 多个英雄和技能可以同时计时；
4. 悬浮层不会遮挡或抢夺游戏焦点；
5. 语音会确认成功记录，但不会逐秒播报；
6. 冷却数据缺失时不会生成虚假精确倒计时；
7. 程序刷新或重启后可以恢复当前对局的活动计时；
8. 不读取游戏内存、不注入游戏、不自动执行游戏操作。

## 12. 主要风险与处理

### 12.1 语音识别错误

通过英雄别名、模糊匹配、待确认状态和重复确认降低误记录。

### 12.2 用户报时晚于实际释放

第一版明确显示“预计”倒计时；后续加入“几秒前”表达和快捷键微调。

### 12.3 知识库数据不完整

没有可靠资料时显示“冷却未知”，不强行套用普通倒计时。

### 12.4 网络语音服务中断

语音服务采用独立适配层；服务失败时保留已有倒计时，并在悬浮层提示语音服务不可用。

### 12.5 对游戏环境的兼容性

只使用麦克风、普通窗口和悬浮层，不接触游戏进程、内存或输入控制，降低兼容和安全风险。

## 13. 结论

该功能最适合在现有项目中新增语音输入层，把语音解析出的技能事件接入已有的冷却计算和悬浮层，而不是重新建立一套独立的技能系统。

推荐的最小闭环是：

```text
“小象助手，妲己放大了”
  → 识别英雄和技能
  → 查询知识库
  → 创建冷却事件
  → 悬浮层显示
  → 语音确认
```
