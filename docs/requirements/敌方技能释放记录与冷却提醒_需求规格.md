# 敌方技能释放记录与冷却提醒 · 需求规格

版本：v0.1；日期：2026-09-09；状态：需求评审稿，尚未按本文完成实现和验收。

## 1. 目标与已确认需求

系统在持续观察游戏画面的过程中，自动识别敌方英雄释放了哪个技能，记录释放时间，在有可靠冷却依据时显示剩余倒计时，并在预计冷却结束时提醒用户注意该技能。

用户已明确选择：**系统从游戏画面自动识别，人工补录或纠正。** 正常流程不要求用户逐次点击登记；人工方式用于漏识别、误识别和特殊情况。仅提供手动计时，不能视为这项需求完成。

本文规定的是目标行为。现有代码、历史方案中的实现描述和测试结果，均不能替代本文的需求验收。需求写清楚后，再据此安排代码工作；本轮保持代码修改暂停。

## 2. 使用场景与范围

### 2.1 正常使用流程

1. 用户选择游戏画面来源，启动本局连续观察；确认或修正系统识别出的双方阵容。
2. 系统发现敌方某英雄施放技能，核对英雄、技能和证据后，自动记录该次释放。
3. 系统查询该英雄该技能在本局适用的冷却规则，结合已知技能等级和冷却影响因素判断能否计时。
4. 能确定冷却时，自动展示倒计时；只能确定范围时，展示预计范围；无法计算时，显示“已记录释放，冷却未知”。
5. 冷却将结束时给予轻量提示，到点提醒“敌方 ×× · ×× 技能预计可用，请留意”。
6. 用户发现误差时，可修改英雄、技能、释放时间或冷却依据，也可撤销误记录；修改同步到同局大屏。

### 2.2 功能范围

| 范围 | 本需求口径 |
| --- | --- |
| 主要对象 | 敌方英雄主动技能；优先支持大招、关键控制和位移技能 |
| 正常入口 | 连续游戏画面中的自动识别；单张截图只辅助核对，不能凭静态画面虚构先前的释放时间 |
| 人工兜底 | 补录漏掉的施放、只登记已知剩余时间、修正或撤销错误记录 |
| 展示 | 工作台与同局大屏的常驻技能面板；提示不抢焦点、不阻塞游戏操作 |
| 提醒方式 | 默认文字和颜色提示；语音、系统通知和手机推送不列入本次范围 |
| 技能覆盖 | 先建立经验证的英雄 / 技能清单，在界面标明覆盖范围；知识库有该英雄不代表已支持自动识别全部技能 |
| 特殊机制 | 多段施放、充能、刷新、冷却起点特殊的技能须单独定义并验证；未经支持的机制只记录可见事实，不套用普通倒计时 |
| 扩展对象 | 己方技能、召唤师技能和装备主动技能可另行扩展，不作为敌方技能需求完成的替代项 |

开发前还需在支持清单中明确首批英雄 / 技能、游戏版本、画面视角与分辨率、运行硬件，以及各技能的冷却资料来源。文中的验收数字是建议目标，不是已验证能力。

## 3. 功能要求

### R1. 自动识别施放事件

系统应识别“某个敌方英雄在某个时刻施放了某个技能”，而不只输出“画面出现技能特效”。每个自动事件必须能关联本局、敌方英雄、技能、采集时间和识别证据。

- 使用连续画面的施法动作、对应技能特效及前后变化进行核对，排除普攻、皮肤特效、己方技能和其他英雄的相似效果。
- 英雄归属、阵营或技能无法确认时，保留为待确认候选；不得创建确定的技能倒计时。
- 低置信或互相冲突的结果不触发到点提醒。置信度阈值须通过实际样本校准，模型自报高置信度不能代替验证。
- 事件时间来自画面采集时间及可靠的局内时间，不能把模型返回时间当作释放时间。推理耗时应从剩余时间中扣除。
- 无法定位到单一时刻时，保留释放时间区间，例如“局内 04:45～04:46”，后续计时沿用该不确定性。
- 同一段持续特效或同一批画面重试只生成一次施放记录；确有新的施放证据时创建新事件。不能因为旧倒计时尚未结束，就一律忽略新的施放。
- 漏掉一次施放后，不能仅凭时间推断敌方“应该已经放过技能”。

### R2. 记录释放与冷却起点

每次施放记录至少包含：对局、阵营、英雄、技能、释放时间或时间区间、冷却起点、记录来源、识别置信度或人工确认状态、冷却依据、预计就绪时间及当前状态。

“释放时间”和“冷却开始时间”分别记录。普通技能可按已核验规则以施放开始计冷却；若技能在施放结束、第二段施放或其他事件后才进入冷却，必须取得对应事件，不能统一从第一次特效出现开始计时。

人工补录默认表示刚刚施放，也允许填写“已过多少秒”和已知的局内释放时间。只知道剩余时间时，保存登记时刻与剩余秒数，释放时间保持未知。

### R3. 冷却依据与计算

每个已支持技能须维护适用版本、各技能等级基础冷却、冷却开始条件、冷却缩减规则、是否受特殊刷新或充能影响，以及资料来源和核验日期。

- 技能等级、装备及其他冷却影响因素应来自可核对的画面或人工输入；未知字段保留未知。
- 对普通百分比冷却缩减机制，只有核验该技能适用时，才使用“实际冷却 = 基础冷却 ×（1 − 有效冷却缩减）”。上限、例外和其他计算机制按本局版本处理。
- 如果能确定有效上下界，输出冷却范围；无法取得可靠范围时，不显示精确秒数。
- 支持用户直接填写本次确认的实际冷却，覆盖自动推算；必须标为人工校正并保留原依据。
- 冷却期间发现等级、装备或状态改变时，按已核验规则判断是否影响本次冷却；规则未知则降为待确认，不能随意重算一个确定时间。

计时规则：

| 情况 | 计算与展示 |
| --- | --- |
| 冷却起点和冷却时长均已知 | 预计就绪 = 冷却起点 + 实际冷却；剩余 = max（0，预计就绪 − 当前有效时间） |
| 起点或时长只有区间 | 最早就绪 = 最早起点 + 最短冷却；最晚就绪 = 最晚起点 + 最长冷却；展示剩余范围 |
| 只确认剩余时间 | 预计就绪 = 确认时刻 + 已确认剩余时间；不反推释放时刻 |
| 冷却资料或起点不可靠 | 显示“已记录释放，冷却未知 / 待确认”，不触发确定到期提醒 |

精确倒计时以秒显示，正数向上取整，到期显示状态文字，不显示负数。范围计算应明确仍缺少哪些信息。

### R4. 时间推进与异常处理

- 计时优先与可靠的局内时间对齐；局内时间暂不可读时，用最近一次可靠的游戏时间与本地经过时间续算，并标为估计。
- 游戏实际暂停、录像暂停时，暂停对应游戏时间的推进；录像倍速影响计时推进，不能始终按现实一秒扣一秒。
- 回放跳转时，恢复该位置对应的有效事件状态；无法恢复时撤下受影响的倒计时，显示待重新观察，不能沿用跳转前的记录。
- 单纯停止视觉识别不等于游戏暂停。已确认的计时记录应保留；画面断流或无法确认游戏是否继续时，展示“观察中断，时间待校准”，暂停新的强到期提醒，恢复后校准。
- 模型处理积压时，过时事件可补入历史，但不能以旧施放时刻重新开启完整冷却。只有时间和后续状态仍有效时才恢复当前计时。
- 页面刷新、浏览器后台节流或设备休眠后，以恢复的有效时间重新计算；不能依靠累计执行了多少次刷新回调来计时。

### R5. 倒计时与提醒界面

同一对局可以同时显示多名敌方英雄的多个技能。卡片至少包含英雄、技能、剩余时间或范围、状态及来源；展开后可查看释放时间、预计就绪时间、冷却依据和纠错入口。

| 状态 | 示例文案 | 提醒行为 |
| --- | --- | --- |
| 待确认 | “疑似王昭君施放 3 技能，待确认” | 不显示确定倒计时，不弹到期提示 |
| 冷却未知 | “已记录释放，冷却未知” | 提供补录入口 |
| 预计冷却中 | “王昭君 · 凛冬已至 · 预计剩余 25 秒” | 常驻卡片 |
| 即将就绪 | “预计 5 秒后可用” | 最后 5 秒变色，保留文字区别，不只依靠颜色 |
| 进入可能就绪区间 | “可能已可用，最晚预计 5 秒后就绪” | 在最早就绪时轻量提醒一次，明确仍有不确定性 |
| 预计就绪 | “敌方王昭君 · 凛冬已至预计可用，请留意” | 精确到点或到区间最晚边界时，展示醒目文字提醒一次 |
| 已确认可用 | “已确认可用 · 人工确认 / 可读技能状态” | 只有新的直接证据才能进入该状态 |
| 时间失效 / 观察中断 | “时间待校准” | 停止强到期提醒，显示失效原因 |

仅凭倒计时归零，不能把状态改成“已确认可用”。技能计时信息也不能单独触发“现在强开”的战术建议。

提醒规则：

- 到点提示建议持续 5 秒；提示结束后，卡片继续保留“预计可用”状态，直到新施放、纠正、移除或对局结束。
- 同一事件在同一显示端的每个提醒阶段只提醒一次；刷新、重连、重复识别和重复同步不能反复弹出。
- 工作台和大屏各自展示；同一秒内多个技能到点合并为一条提示，卡片分别更新。提示不覆盖当前主战术建议。
- 允许关闭弹出提示，常驻状态继续更新；被撤销或已被新施放替换的事件不再提醒。
- 页面关闭期间不发系统通知；重新打开时恢复最新状态，已结束对局不补发技能提醒，仍在进行的对局可合并提示尚未展示的有效到点事件。

### R6. 人工补录、纠错与多次施放

用户可以补录、修改或撤销单次记录。修改英雄、技能、释放时间或冷却后，系统重新计算，并同步到所有显示端；历史保留修改前后内容及来源。

- 错认英雄或技能：修正归属，不再保留错误对象的活动倒计时。
- 释放时刻错误：修改时刻或已过秒数，预计就绪时间同步变化。
- 冷却推算错误：录入确认的实际冷却或剩余时间，不必重新虚构一次施放。
- 技能发生刷新：记录刷新依据，结束或修正原计时；没有可靠证据时标为待确认。
- 同一技能再次施放：普通技能以最新有效事件作为活动计时，旧事件进入历史；多段和充能技能按各自规则处理，未经支持时不冒充普通技能计时。
- 人工修正后的同一事件，不应被迟到的旧模型结果覆盖；出现新的独立施放事件时，仍可正常登记。
- 提供单条移除和本局清空；清空活动计时不删除历史，后续新施放仍能自动记录。

### R7. 对局保存与大屏同步

释放事件、当前状态、纠错历史及提醒去重信息应按对局保存。刷新、短暂断线和服务重启后能够恢复；新建对局不带入上一局的活动计时。

同局大屏应同步新增、修改、撤销、到期状态和对局结束。迟到的旧消息不能覆盖新状态，不同显示端不能各自重新开始一轮完整冷却。

游戏结算经可靠识别或用户确认后结束本局计时，不应要求用户先生成海报才能停止提醒。误判结算可由用户纠正；恢复计时前需重新校准时间和事件有效性。

建议容量：每局最多 40 个活动计时，历史界面默认展示最近 100 条。达到容量时不得静默丢弃既有记录；提示整理已结束记录，并明确新事件是否已进入历史。最终上限可在交互评审中调整。

## 4. 记录信息要求

以下为业务信息要求，尚不锁定接口、数据库表或字段命名。

| 信息 | 必要性与规则 |
| --- | --- |
| 对局与事件编号 | 必填；一次真实施放对应一个可追踪事件 |
| 阵营、英雄、技能 | 必填；区分已确认归属和候选归属 |
| 释放时间 | 保存采集时间、已知局内时间及必要的上下界；未知不补为 0 |
| 冷却起点 | 明确起点事件与时间；可与释放时间不同 |
| 记录与处理时间 | 用于区分施放发生、画面到达和识别完成，核对延迟 |
| 来源与证据 | 自动识别 / 人工补录 / 人工修正；关联帧编号、证据摘要、模型版本或人工说明 |
| 冷却依据 | 适用版本、技能等级、已知冷却影响、基础值或确认的实际值、资料来源；保留未知项 |
| 预计就绪 | 单一时刻或上下界；保留原始依据与后续修正 |
| 当前状态 | 候选、预计冷却中、可能就绪、预计就绪、已确认可用、待校准、撤销、被新施放替换、对局结束 |
| 修订与提醒 | 修订先后顺序、已展示的提醒阶段、各显示端去重信息 |

默认保存结构化事件及证据摘要，不额外要求全程保存视频。需要影像核验时可开启本地事件留图；未留图的历史记录明确标注“无留存画面”，不能声称有录像证明。

## 5. 示例

以下冷却数字只用于验收计算，不代表任何版本的官方技能数值。

### 示例 A：自动识别并扣除推理耗时

画面显示敌方王昭君在局内 04:45 施放 3 技能。该技能本次适用冷却已经确认是 30 秒，且规则确认从施放开始计算。识别结果在局内 04:48 返回。

系统自动记下释放时间 04:45、预计就绪 05:15，首次展示约 27 秒倒计时。到 05:10 进入最后 5 秒提示，到 05:15 提醒“预计可用”。不能从识别完成时重新计 30 秒。

### 示例 B：释放时刻或冷却只知道范围

释放时刻为局内 04:45～04:46，确认冷却范围为 25～30 秒，则预计就绪区间为 05:10～05:16。在 05:10 提醒“可能已可用”，到 05:16 更新为“预计可用”；整个过程不显示“已确认可用”。

### 示例 C：人工补录与只知道剩余时间

人工确认某技能 5 秒前释放，本次实际冷却为 30 秒，则登记后约剩余 25 秒。若只确认现在还剩 12 秒，则从确认时刻计 12 秒，释放时间仍为未知。

### 示例 D：画面中断与暂停

技能还剩 20 秒时游戏实际暂停 10 秒，恢复后仍约剩 20 秒。若只是采集断流 10 秒，系统显示“观察中断，时间待校准”；恢复后发现游戏确实继续运行，则校准到约剩 10 秒。两种情况不能混为一谈。

## 6. 验收标准

### 6.1 功能验收

| 编号 | 操作 / 条件 | 通过标准 |
| --- | --- | --- |
| A01 自动登记 | 已支持敌方英雄施放已支持技能 | 用户不点登记，系统创建英雄、技能和释放时间正确的记录 |
| A02 自动倒计时 | 自动事件具有有效冷却依据 | 自动显示与事件时刻对应的倒计时，扣除识别耗时 |
| A03 到期提醒 | 有效计时到达就绪时刻 | 显示英雄、技能及“预计可用”，同事件不重复弹出 |
| A04 区间状态 | 起点或冷却只知范围 | 正确显示范围及最早 / 最晚提醒，不伪装精确时刻 |
| A05 未知条件 | 技能等级、冷却起点或必要数据未知 | 保留释放事实，展示未知 / 待确认；无虚构倒计时 |
| A06 防误识别 | 普攻、己方技能、相似特效、冲突结果 | 不产生已确认的敌方技能计时；必要时进入候选 |
| A07 去重与再次施放 | 连续特效多帧、识别重试，随后真实再次施放 | 首次只记一条；新施放正常建立新事件、保留历史 |
| A08 人工兜底 | 补录、修正英雄 / 时间 / 冷却、只填剩余秒数、撤销 | 计时与历史正确更新；只填剩余时间不编造释放时刻 |
| A09 防旧结果覆盖 | 人工修正后旧识别结果或旧同步消息迟到 | 已修正状态保持有效，不恢复错误倒计时 |
| A10 暂停与回放 | 游戏暂停、录像暂停、倍速、跳转 | 按 R4 推进、冻结或失效；不按错误时间继续提醒 |
| A11 断流与恢复 | 采集中断、识别停止、页面刷新、服务重启 | 保存记录、标明时间可信度，恢复后校准并去重 |
| A12 多目标同步 | 多英雄多技能，同局两个显示端 | 各自计时正确，新增 / 修改 / 撤销同步，计时显示差异不超过 1 秒 |
| A13 对局边界 | 新建对局、可靠结算、手动结束 | 不串局；结束后停止技能提醒，历史可查 |
| A14 特殊机制 | 多段、充能、刷新或特殊冷却起点 | 已支持的按核验规则处理；未支持的不套用普通倒计时 |
| A15 交互与容量 | 多技能同时到点、关闭提示、达到容量 | 提示合并且不抢焦点；关闭弹出仍能看状态；容量满不静默丢记录 |

### 6.2 自动识别质量与性能目标（建议，需在指定环境验收）

- 按首批支持清单逐技能验收，使用人工标注的真实画面，覆盖不同皮肤、遮挡和混战；每个技能至少 50 次施放样本，并加入相似技能、普攻和未施放的负例。开发样本与验收样本分开。
- 事件准确率目标 ≥95%，定义为“正确匹配英雄、技能和同一次施放的事件数 / 系统输出事件总数”；召回率目标 ≥90%，定义为“正确识别事件数 / 支持范围内可见真实施放数”。各技能分别报告，不能只给总体平均值。
- 完全离屏、遮挡导致无法判断的施放不宣称可识别；此类样本数量、未知输出比例和未覆盖技能须单独披露，不能用大量不输出掩盖低覆盖。
- 已输出事件的释放时间误差 P95 目标 ≤1 秒；时间区间输出另报区间覆盖率和宽度，不能用无限放宽区间代替识别准确性。
- 在指定硬件上，施放发生至首次有效提示的端到端延迟 P95 目标 ≤2 秒；超过该目标的技能不宣称具有经验证的即时提醒能力。
- 时间基准有效、页面前台运行时，倒计时显示误差目标 ≤1 秒，到期状态更新延迟目标 ≤1 秒。浏览器休眠恢复应重新校准，而不是补跑遗漏的秒数。
- 冷却计算单独验证版本、等级、缩减和特殊规则；时间计算正确与视觉识别正确分别报告。未知条件输出未知属于正确降级，不能统计为已成功给出准确倒计时。

上述指标未达成前，应继续限制支持清单或标记实验功能。手工录入、模拟模型响应、接口测试和截图演示均不能替代敌方自动施放识别验收。

## 7. 后续开发顺序与完成条件

1. 先评审本需求，确定首批支持清单、时间规则、冷却数据来源和验收环境。
2. 据此梳理现有预研代码的可复用部分与缺口，再开展事件记录、计时、纠错和同步的实现。
3. 接入敌方自动施放识别，验证身份归属、时间、去重、冷却依据和失败降级。
4. 在真实画面上走通“自动识别 → 自动记录 → 倒计时 → 到期提醒”，再执行 A01～A15 和识别质量验收。
5. 按实际结果更新 README 和交付计划，明确已支持英雄 / 技能、通过的环境及未通过项。

最终完成条件：在明确支持的游戏环境与英雄 / 技能范围内，正常路径无需逐次人工登记即可完成闭环，人工补录纠错可用，保存与同步通过验收，且所有“预计”与“已确认”状态表达正确。
