# 电竞室 AI 助教方案：Qwen3-VL-8B 屏幕观察 + 对线压制 + 团战与节奏建议

本稿基于《gemini-code-1788927958966.md》修订，并合并《电竞室_AI_助教项目极简迭代计划_知识库增强版(2).md》中的 BP 克制英雄、阵容分析、分阶段打法、局中四类决策、行为回顾与扫码战报功能。按用户最新确认，采集对象为电脑屏幕，采用电脑桌面/窗口直捕、Qwen3-VL-8B 视觉理解、外部战术 API 和屏幕侧栏文字提示。

本文为功能与实施方案，尚未完成硬件压测或游戏识别实测；性能数字不得当作已验证能力。新增功能区分首期交付与进阶迭代，并同步调整数据依赖、排期和验收。

2026-09-09 新增需求：用户明确要求从游戏画面**自动识别敌方技能施放，人工补录或纠正**，记录释放时间并提供冷却倒计时与到期提醒。详细规则统一见 [敌方技能释放记录与冷却提醒 · 需求规格](敌方技能释放记录与冷却提醒_需求规格.md)。当前先评审需求，代码工作暂停；现有手动计时预研不代表自动识别闭环已完成。

最新功能口径：保留 BP 同路对位的清线、换血与压制分析，并根据用户新增要求，借鉴灵宝公开报道中的情境提醒与互动方式，补充团战、资源节奏、回城补给、出装问答和提示风格。对线与团战分别建模，团战作用和全局胜率不作为对线压制的替代指标。

核心要求：系统持续采集电脑上指定的游戏窗口、显示器或屏幕区域，将图片送入 Qwen3-VL-8B，通过视觉识别与跨帧状态判断，自动生成、更新或撤销建议。BP、对局阶段切换、局中事件和结算识别均由画面驱动。玩家选择观察目标并启动监测后，正常使用无需逐次上传截图、填写局面或点击“分析”。

Qwen3-VL-8B 接收采集程序提供的图像或带时间信息的画面序列。屏幕捕获、持续调度、状态记忆与 HUD 展示由外围程序实现。本方案以电脑端直接捕获为默认输入，手机仅用于可选的扫码查看战报。

## 一、评审结论与首期范围

Qwen3-VL-8B 可以作为屏幕理解的候选核心，但通用视觉能力不等于已具备稳定的游戏状态识别能力。项目成败主要取决于真实游戏画面的字段识别、跨帧状态维护、过期建议拦截和目标硬件性能。

首期定位为电脑上的单游戏、固定界面配置、单路会话辅助提示 Demo。具体游戏、游戏版本、玩家视角、操作系统、显示器配置和推理主机显卡/显存需在第一天登记。下文沿用附件中的《王者荣耀》英雄与 5v5 场景作为功能示例；实际观察对象以电脑运行的游戏或模拟器窗口为准，其他游戏需适配英雄、规则和界面。

首期交付：

- BP：持续识别同路对位及禁选变化，推荐最多 3 名具备已核验对线依据的候选，解释清线、消耗、换血和阶段条件；视觉确认用户锁定后切换为当前英雄的对线打法。实际分路不确定时使用条件建议。
- 加载：视觉识别完整阵容后生成初始打法，结合后续已确认的阶段和事件调整或撤销相关提示。
- 局中：持续采样，首期选择 1 类对线事件与 1 类团战准备/撤退事件上线，例如停止前压、等队友到位；目标准备和回城补给按识别验证结果追加。完整技能空档、实时团战中的精细指挥分阶段验证。
- 敌方技能计时增补：在经验证的英雄 / 技能清单内自动识别施放，记录事件时刻，依据本局冷却规则自动计时和提醒；人工登记作为补录纠错。首批清单、版本与验收环境待需求评审明确，不能将全英雄知识条目数量视为自动识别覆盖率。
- 互动：支持基于当前画面的文字提问、查看建议依据、关闭主动提示和选择表达风格；保持无语音、文字 HUD 的交付方式。
- 赛后：可见结算数据摘要、具体改进建议、下一局训练目标和扫码战报；有局中事件记录时，补充有限的过程回顾。
- 呈现：局中卡片优先一行行动建议，必要时增加一行依据；详细战报放到赛后页面。

小地图多人追踪、持续敌方动向判断、复杂接团/拉扯/撤退/换资源决策、动态出装建议和自动行为追踪列入进阶迭代，达到单项识别与战术验收标准后再启用。首期 BP 与打法建议先覆盖约定的英雄及已核验关系，覆盖范围在界面和交付清单中说明。

### 1.1 实时视觉驱动的运行方式

系统循环执行：**采集最新画面 → Qwen3-VL-8B 提取可见事实 → 与近期观测比较 → 判断当前局面及变化 → 结合战术依据给出建议 → 继续观察并校验建议是否有效**。

Qwen3-VL-8B 负责画面理解；跨帧状态、规则和外部战术模型共同完成局面判断与行动建议。战术资料提供英雄机制和应对依据，是否在此刻提醒由当前视觉状态决定。

| 视觉确认的变化 | 系统自动处理 | 用户看到的效果 |
| --- | --- | --- |
| 敌方同路候选、己方分路或禁选变化 | 重新检查同路对位、候选资格和对线条件 | 更新 BP 对线参考卡片 |
| 用户从预选变为正式锁定 | 结束选人推荐，生成已选英雄的应对方法 | 卡片切换为“本局怎么打” |
| 进入对局，计时器/目标状态达到已支持事件条件 | 结合连续观测确认当前阶段与提醒必要性 | 自动显示资源准备或风险提示 |
| 已支持敌方技能的施放获得可靠画面证据 | 自动记录释放时刻与冷却依据，扣除推理耗时，维护多技能状态 | 显示预计剩余时间或范围，到点提醒「预计可用」；条件未知时保留未知 |
| 原建议的前提改变，例如目标已结束、关键状态过期 | 撤销旧判断，必要时重新生成 | 过时卡片撤下或替换 |
| 出现稳定结算页 | 自动提取可见数据并关联本局事件记录 | 生成战报及训练建议 |

每次有效观测都更新状态并检查已有建议。只有值得提醒的变化才触发新卡片或外部 API，保持后台持续观察、前台少量提示。

“实时”指在线连续采样、持续判断和及时反馈；采样频率与端到端延迟在目标硬件上实测。首期先验证较慢的选人、资源和状态变化；短暂技能与瞬时走位需要更快且经验证的专用识别能力。

## 三、画面采集与模型部署

### 3.1 直接捕获电脑窗口或桌面

首期按 Windows 电脑设计，先支持一个明确的观察目标：指定游戏窗口、某个显示器或该显示器上的区域。目标可为电脑游戏窗口、模拟器窗口，或实际显示游戏画面的浏览器窗口。

| 采集方式 | 适用场景 | 需要验证的条件 |
| --- | --- | --- |
| Windows Graphics Capture 窗口捕获 | 优先隔离指定游戏/模拟器窗口 | 目标应用、窗口模式、遮挡和最小化状态下的实际输出 |
| Desktop Duplication，如 DXcam 封装 | 采集指定显示器，再裁剪游戏区域 | 显示器选择、坐标映射、HDR/色彩格式与全屏模式兼容性 |
| `mss` 截图 | 低频采样原型与兼容性验证 | 实际帧获取速度、画面完整性和 CPU 开销 |

- 先选一条捕获路径跑通并固定依赖版本。OpenCV 用于裁剪、缩放和图像处理，桌面捕获接口由所选采集模块提供。
- 保存观察目标及区域配置；窗口移动、尺寸变化、DPI 缩放或显示器切换时更新坐标，无法可靠定位时暂停该目标的判断。
- 区分“内容没有变化”和“捕获失效”。黑帧、目标关闭、访问失败或可确认的断流应使动态状态过期，暂停新建议。
- 分别验证窗口化、无边框和独占全屏；不支持的模式明确列入兼容性清单，不能静默换成其他应用画面。
- 游戏正常显示与 AI 分析并行运行。建议可放在独立侧栏窗口、另一显示器或大屏；优先使用不包含助教窗口的捕获目标。采用桌面区域捕获时，HUD 应放在采集区域之外，防止建议文字被再次识别为游戏信息。
- 本机直接获取图像时不需要额外的视频编码/解码链路。若推理部署在另一台主机，再单独记录图像压缩和传输开销。

### 3.2 固定模型与推理配置

首轮优先评估 `Qwen/Qwen3-VL-8B-Instruct`，以短输出的状态抽取为目标。推理框架选择一个跑通后固定版本，避免在 vLLM / Ollama 之间同时维护两条未经验证的路径。

Qwen 官方文档推荐 vLLM，并说明 Qwen3-VL 支持需要 `vllm>=0.11.0`；具体模型、量化格式和运行环境仍需验证。若现有环境为 Windows，vLLM 路线应把适配的 Linux / WSL2 GPU 环境验证纳入排期。若选择 Ollama，则先验证实际版本、模型包、视觉输入和结构化输出支持情况。

必须登记：GPU 型号与显存、驱动、运行环境、模型版本、权重精度、推理框架版本、图像像素预算、同时输入图片数、输出 token 上限、并发路数。

游戏和 Qwen3-VL-8B 在同一台电脑运行时，需要同时测游戏帧率/帧时间、推理耗时和显存占用。先通过裁剪、输出长度与采样频率控制开销；若资源竞争仍影响游戏体验，可把模型放到独立 GPU 或局域网推理主机，屏幕采集仍在游戏电脑上完成。

### 3.3 分阶段识别，控制视觉开销

- 选人/加载：持续识别槽位、英雄名称、阵营、自身位置、禁用英雄及锁定状态；悬停/预选与正式锁定分别记录，稳定字段复用，画面变化后自动更新。禁选或分路不可读时保留未知，可提供人工纠错入口，但自动视觉链路不依赖逐次人工输入。
- 局中：先做低成本的界面分类和区域变化检测，再按事件需要提取小地图、计时器、血条等区域。Qwen 负责区域语义理解，必要时结合 OCR、模板或专用检测器处理细小数字与图标。
- 结算：待页面稳定后分区域读取；多页数据按对局和玩家槽位合并，未出现的字段留空。
- 全屏低分辨率图可以提供布局上下文；小字区域单独保留清晰裁剪。比较全屏与裁剪组合的准确率、耗时，再决定输入方案。
- 1–2 FPS 仅作为初始抽样配置，不代表能捕捉所有短暂技能、瞬时血量变化和小地图闪现。
- 每路最多保留一个等待处理的最新帧；处理完成后取最新帧，丢弃中间旧帧。分析队列不得无限积压。

减少外部文本 API 调用只能降低一部分成本。连续视觉推理仍可能是主要算力瓶颈，应同时测量单路 GPU 占用和多人并发容量。

## 四、结构化状态与跨帧记忆

不要只把视觉 JSON 直接送给战术模型。增加可校验、可过期、可追溯的状态层。

| 状态字段 | 要求 |
| --- | --- |
| `session_id`、`frame_id`、`state_version` | 区分对局、证据帧和状态版本，防止旧请求污染新对局。 |
| `captured_at`、`received_at`、`processed_at` | 记录画面采集、服务接收及识别完成时间；能取得源时间戳时做时钟映射。 |
| `phase`、`game_time_s` | 阶段区分选人、加载、对局、结束动画、结算、未知；计时器不可见时不得填 0。 |
| `player_context` | 明确在辅助谁、队伍方向、操控英雄/分路，避免给错阵营的建议。 |
| `lane_context` | 记录我方英雄、敌方实际对位、所在路线及对位确认状态；记录可见等级、血量/资源、装备、兵线位置与数量、塔距、支援威胁和技能事件证据。缺失字段保留未知并分别设置有效期。 |
| `bp_context` | 记录禁选/选人阶段、双方已锁与预选英雄、禁用列表、是否轮到用户、用户是否已锁定、可读的剩余时间；未读到的字段标为未知。 |
| `player_preferences` | 可选的擅长英雄和可用英雄池，仅用于个性化排序，不是启动实时判断的前提；当前分路优先从可靠画面识别，必要时允许纠正。无法从画面确认的熟练度等信息不猜测。 |
| `observations` | 每个字段记录值、观测范围、来源帧、证据区域和最近确认时间。 |
| `source` | 区分 `observed`（直接读到）、`derived`（按规则计算）、`unknown`（不可知）。 |
| `valid_until` | 动态状态设置过期时间；不同字段分别设置有效期。 |

关键约束：

1. 未知用 `null` / `unknown`，不以 0、死亡、目标不存在代替未识别到。
2. 英雄、血量范围、时间和阵营做枚举/范围校验；非法 JSON 或字段冲突不得进入事件判断。
3. 模型自报置信度仅作为线索，不能直接当作经过校准的正确概率。结合清晰度、字段一致性和标注集结果决定是否采用。
4. 趋势来自带时间戳的连续状态；连续帧一致只是过滤抖动的方法，不能证明识别一定正确。
5. “小地图当前可见敌方 2 人”“敌方当前存活 2 人”“目标区域敌方 2 人”是三种不同信息，不得互相替代。
6. 敌方失去视野后只保留带时间的最后观测位置，过期后标为未知。
7. 目标倒计时优先读可见 UI；规则推算需要当前版本规则及可靠的前置事件，并标明推算来源。不能只凭对局时间反复套固定刷新周期。

识别提示词应限定：只提取指定字段，附来源，无法判断时留空。屏幕内聊天、昵称和其他文字作为被观察的数据，不能覆盖识别与战术服务的指令。

## 五、事件触发、建议有效期与降级

建议链路：

```text
电脑游戏窗口 / 指定显示器区域（游戏正常显示）
                  ↓ 桌面或窗口捕获，获取最新帧
         阶段识别 + 按需区域裁剪
                  ↓
       Qwen3-VL-8B / 必要的 OCR 或检测器
                  ↓
       字段校验 → 跨帧状态 → 事件判断
                  ↓
       按阶段处理：BP 候选筛选 / 局中事件规则
                  ↓
       按英雄、对位和事件查询已核验战术事实
                  ↓
     简单确定事件：本地模板；候选解释/复杂建议：外部 API
                  ↓
       候选与依据校验 + 过期检查 + 去重
                  ↓
      WebSocket → 电脑侧栏 / 副屏 / 大屏 HUD
```

每类事件必须定义：前置条件、必要证据、连续确认窗口、触发阈值、冷却时间、优先级、失效条件和可用模板。

以上链路随视频采样持续运行。建议发出后仍检查最新视觉状态；无需等待下一次 API 返回或用户操作才撤销失效卡片。界面阶段由视觉状态机自动切换，阶段不确定时保留未知并暂停依赖该阶段的新建议。

例：识别到目标倒计时进入预告窗口后，经连续观测确认且本轮尚未提醒，触发一条准备目标的提示。若倒计时不可读或规则版本未确认，则不触发确定时间的建议。

- 防抖初值可采用连续 2–3 次观测或一个短时间窗口，最终按事件速度和误报表现调整；这会增加延迟，须计入预算。
- 相同事件去重，并采用进入/退出不同阈值，减少在边界反复提示。
- API 请求绑定 `session_id`、事件编号、来源状态版本、依据时间及有效期。返回后重新检查必要状态；过期、事件取消、阶段变化或对局结束时丢弃。
- HUD 到期自动撤下，断线重连不重放过期提示。断流时清空依赖动态状态的卡片。
- API 超时、限流或不可用时，只有依据仍有效才用本地模板，否则跳过；局中不反复重试旧事件。
- 设定每分钟请求上限、同类事件冷却、每局费用上限及并发限制；取消与当前局面无关的等待请求。
- 提示长度建议：局中行动句约 15–30 个汉字，按需补一行依据；赛前约 60–100 字；赛后约 120–150 字。

### 6.2 BP 对线压制选人

目标：在玩家仍可选择时，针对敌方同路英雄给出候选，说明谁更容易清线、争取换血收益或取得线权，以及优势成立的条件。英雄池与熟练度用于资格筛选和选择偏好，不能将“有团控、能保护后排”直接视为对线压制依据。

处理流程：

1. **确认 BP 状态**：从连续画面自动识别双方阵营、敌方已锁英雄、己方已选英雄、禁用列表和用户选人状态。预选英雄只标为暂定，不当作最终阵容；用户无需手动录入每次选人。
2. **确定玩家需求**：优先从可靠视觉信息确定当前分路；用户可选提供的擅长英雄和可用英雄池用于排序。分路未知时给带分路标签的参考候选，不能假定用户的分路、英雄可用性或熟练度。
3. **生成并过滤候选**：按“游戏版本 + 分路 + 我方候选 + 敌方对位 + 等级/装备阶段”查询已审核对位资料，再按当前模式规则剔除禁用、占用和已知不可用英雄。只覆盖英雄名称但没有该对位资料时，不补造压制结论。
4. **按对线条件排序**：比较清线速度与安全性、射程、消耗/续航、短换血和持续对拼、技能空档、等级节点、兵线依赖及防抓代价。说明评价适用的阶段与熟练度条件，不显示未经验证的压制分数或胜率提升。
5. **输出最多 3 名**：每名显示“我方英雄 vs 敌方对位”、可争取的对线优势、具体打法和优势失效条件。候选不足时按实际数量展示。
6. **随 BP 更新**：实际对位改变、换线、禁选变化或用户锁定后重新校验。用户锁定后撤下换英雄建议，转为当前英雄的对线打法；进入对局后以实时状态判断能否执行。

对位优先支持对抗路、中路和发育路。发育路遇到辅助在场时须结合局部人数和双人配合，不能机械套用射手单挑结论。打野、游走通常没有固定单人对线，不强制给出同路压制评级。多分路英雄在 BP 时只能作为可能对位，进入对局后需要用连续画面确认。

卡片结构示例（英雄对位强弱需当前版本验证）：

> **中路对位 · 王昭君 vs 妲己**  
> 对线计划：尝试用范围技能兼顾清线与消耗，保持安全距离争取线权。  
> 执行条件：关注双方等级、血量、技能状态和兵线；对方控制条件不明时避免近身换血。

每次推荐保留候选、敌方对位、分路、对线维度、等级/装备阶段、优势条件、失效条件、资料 ID 和 BP 状态版本。不能根据“敌方对抗路锁定关羽”就直接认定己方中路英雄可以压制其对线。

### 6.2.1 局中通过视觉判断当前能否压制

将“BP 时的对位潜力”与“此刻的压制机会”分别记录。系统持续观察同路双方和附近威胁，输出 `push`（争取线权）、`trade`（条件允许时短换血）、`hold`（控线/稳线）、`retreat`（停止前压）或 `unknown`（证据不足），并附具体依据与有效期。

- 看双方英雄与实际路线，确认对手身份，换线后重建对位。
- 看等级、血量/蓝量、可见装备以及兵线的数量和位置；不能因英雄资料占优就忽略当前状态劣势。
- 看双方与兵线、防御塔和支援入口的相对位置；兵线优势不直接等于可以越塔。
- 技能空档需要可靠的技能事件、连续追踪及版本规则。画面没看见施法不代表技能可用；不能靠 1–2 FPS 的低频采样承诺识别所有瞬时技能。
- 对方打野未出现时，只能说明其位置未知；不得推导为安全。明确支援威胁出现或关键依据过期后，撤下压制提示。
- 输出“先清线再消耗”“等关键技能空档再短换血”“兵线劣势时先后撤”等可执行建议；未知前提直接影响决策时保持观察。

对线成效评估使用可见且连续记录的清线、换血、兵线控制和回城/阵亡事件；有可靠数据时再统计对位经济或经验差。不能仅凭最终 KDA、团战表现或整局胜负认定压制成功。

### 6.3 阵容加载、对线与前中后期打法

视觉确认双方锁定后，自动生成一张 60–100 字的初始摘要卡；随后根据已确认的游戏阶段、阵容修正和已支持事件调整相关内容。详细内容按需展开，重点包括：

- **己方怎么发挥**：围绕先手控制、保护核心、消耗或边线牵制等已确认阵容特点提出计划。
- **敌方主要威胁**：说明值得注意的突进、控制或持续输出来源，并给出与用户英雄相关的应对。
- **对线注意事项**：依据对位资料描述换血条件、技能保留、防抓站位；对位不确定时标注条件。
- **开局计划**：一级守入口、观察入侵、防止落单等有依据的准备建议。敌方实际开野方向未知时，不把计划写成已发生事实。
- **前中后期目标**：给出当前阵容通常适合的节奏，并说明经济、装备或局势变化会影响执行条件。
- **个人团战职责**：前排开团或保护、后排输出位置、刺客等待机会等，结合英雄资料解释。

首期从加载画面生成初始计划，并通过持续视觉观测判断其是否仍适用；更新范围限于已验证的字段和事件。复杂兵线、经济、装备与技能联动逐步扩充。无法从屏幕确认队友或敌人的技能冷却时，不声称“某英雄有大/没大”；可表达为“确认关键技能可用后再接团”。

### 6.4 战术知识的轻量实现

首期采用 JSON / SQLite 等结构化资料，按英雄 ID、对位、分路和事件类型查询。先维护已审核的英雄和关系子集；无需新增向量数据库或长文档切片检索服务。后续资料规模扩大后再评估检索方案。

| 资料类型 | 最少内容 |
| --- | --- |
| 英雄资料 | ID、名称/别名、适用分路、职责标签、关键机制、使用条件 |
| 对线关系 | 我方英雄、敌方同路英雄、分路、等级/装备阶段、清线/换血等维度、优势与失效条件、资料来源与版本 |
| 全局战术关系 | 阵容搭配与团战限制单独存储，仅用于对应扩展功能，不能混入对线排序 |
| 战术与出装要点 | 分路、游戏阶段、行动建议、必要前提；具体装备建议附适用版本 |
| 来源与审核 | 游戏版本、资料来源、核验日期、审核状态；未核验或失效条目不用于确定性推荐 |
| 事件模板 | 触发条件、必要事实、行动句、失效条件和优先级 |

新增附件及现有英雄资料可作为待审核素材，不能仅因已有“60+ 英雄”条目就视作当前版本验证通过。BP 功能首期验收同时提交覆盖英雄、关系数量和未覆盖场景清单。

向外部 API 提供当前已确认状态、合格候选、命中的已核验事实、短事件历史和未知项，要求返回建议及依据 ID。服务端校验候选范围、响应结构、依据是否存在与是否过期。只告诉模型当前版本不能让它自动获得该版本知识；不允许模型自行补全缺失的克制关系或装备数值。

### 6.5 局中四类决策与证据不足时的处理

团战功能按团前准备、交战中的行动与团后转资源组织。首期优先验证“等人再开”“明确劣势时后撤”等保守事件，精细接团、技能衔接与团中追踪作为进阶能力。以下决策均按必要观测能力逐类启用：

| 决策 | 必要判断 | 提示示例 |
| --- | --- | --- |
| 接团 | 同一交战区域及可支援人数、关键血量/技能、位置或线权、目标价值满足已验证规则 | “先推中线，确认关键技能可用后再接目标团。” |
| 拉扯 | 已确认正在接近/交战，且存在血量、位置或技能上的明确限制 | “先拉开距离，等队友到位再接。” |
| 撤退 | 可靠的局部人数劣势、核心低血量/缺席或迫近威胁，且建议仍可执行 | “队友尚未到位，先退到安全位置。” |
| 换资源 | 当前目标难以安全争夺，另一侧资源可见、可到达且风险已评估 | “暂缓争夺目标，优先处理另一侧已确认安全的兵线。” |

不强制四选一：增加 `observe`（继续观察）和 `no_advice`（本次不提示）状态。人数、技能、位置等决定性前提未知时，不生成确定的强开或换资源指令。更高的模型自报置信度不能替代缺失事实。

统一建议结果至少包含 `decision`、`urgency`、`message`、`evidence_ids`、`conditions`、`state_version` 和服务端确定的有效期。备用动作只在依据足够时显示。电脑游戏画面正常显示，局中侧栏同时展示一条主建议，沿用第五节的过期、去重和降级机制。

按阶段细化用户收到的建议：

- **团前准备**：检查队友是否到位、自身血蓝和可见技能、兵线与目标条件；提醒“先等输出位到场”“先处理兵线再靠近”。
- **团中行动**：在可靠追踪基础上判断拉开距离、保护被切后排或停止追击。战斗变化快，只有实测能及时送达的事件才启用；不做逐帧技能操作指令。
- **团后收益**：结合已确认的存活状态、兵线、防御塔和目标情况，建议推线、转塔、准备资源或回城；胜利动画或一条击杀提示不足以证明可以安全开龙。
- **个人职责**：结合玩家英雄，说明应该保护谁、等待什么进场条件或保留哪类技能；没有可靠冷却证据时，不声称他人关键技能可用。

### 6.6 行为回顾与下一局训练目标

首期记录建议、显示时间和证据；进阶版本在可靠追踪基础上关联建议后的可观察行为：

- 推线后接团：记录兵线变化、移动方向以及何时靠近目标区域。
- 撤退：记录是否拉开距离或进入可确认的安全位置。
- 击杀后转资源：记录随后可见的移动目标、攻击对象和资源变化。
- 交战结果：只记录已确认的死亡、目标或防御塔变化；不知道的经济变化不补齐。

结果使用“观察到与建议一致的行为 / 观察到不同的行为 / 证据不足”，不判断用户主观意图。建议时间窗之外的行为不强行关联；局部画面无法代表整队行为。

赛后将有证据的事件整理为“时间点 → 当时局面 → 提示 → 可观察行为 → 已知结果”，再提出一个可执行的训练目标。若没有足够过程证据，可提供“争夺目标前先确认队友位置”等通用练习，并标明其属于通用建议。一次交战输赢不能直接证明建议正确或用户执行有误。

| 公开报道描述 | 本方案采用的设计 | 证据性质 |

| 依据局内信息主动进行战术提醒 | Qwen3-VL-8B 观察电脑窗口，状态变化后给一条行动建议 | 借鉴已报道的交互方式；视觉实现路线为本项目方案 |
| 根据玩家行为生成情境反馈 | 对已观察到的后撤、转线等行为做简短反馈，附时间与证据 | 借鉴已报道方式；行为识别能力需独立验证 |
| 互动模式与主动对话开关 | 自定义“简短教练 / 展开依据 / 温和鼓励”，支持关闭主动提示 | 模式名称与具体文案为本项目设计，不声称是灵宝官方原样功能 |
| 局内语音与主页互动 | 本阶段使用文字提示和点击式文字提问，交战中减少额外打扰 | 适配已有无语音要求 |
| 完整团战决策、动态装备推荐、详细复盘规则 | 按下表作为项目功能细化，不能标注为已核实的灵宝完整能力 | 本项目新增设计 |

不根据搜索摘要或玩家爆料认定灵宝拥有“精确预测隐藏位置”“自动秒换装备”等能力。本次功能借鉴限于公开可核实的交互方式和用户要求的辅助建议，不接入其未公开接口。游戏内助手与电脑屏幕观察方案的可用信息不一定相同。

### 6.8 团战以外的建议与文字问答

| 功能 | 触发/必要依据 | 提示示例 | 上线条件 |
| --- | --- | --- | --- |
| 目标准备 | 可读目标倒计时、玩家位置、必要的兵线/队友信息 | “先处理中线，再确认队友能否到场。” | 已支持目标规则及倒计时识别通过 |
| 防抓与停止追击 | 敌人最后可见位置、当前可见支援、追击区域与自身状态 | “支援已到河道，先停止前压。” | 只针对明确可见威胁或标注为未知的风险，不报隐藏敌人精确位置 |
| 回城补给 | 自身血蓝、兵线、当前敌方威胁与位置 | “先退到安全位置，再考虑回城补给。” | 不把低血量单独等同于原地回城条件 |
| 团后推塔/转资源 | 可确认的存活状态、可见兵线、塔/目标状态及己方状态 | “兵线已到，先评估推塔，避免追得过深。” | 对资源可达性与风险有足够依据 |
| 出装方向 | 已确认双方英雄与伤害/回复机制、自己可见装备和经济 | “对方回复较多，可考虑补充重伤；先核对已有装备与经济。” | 版本资料可靠；数据不足时只解释方向，不断言立刻购买最优 |
| 当前局面问答 | 用户点击“这波怎么打 / 为什么先退 / 装备怎么选”，关联最新视觉状态 | 用一条行动句加当前证据回答 | 首期可做固定问题；自由文字提问逐步扩展 |
| 玩法与机制解释 | 用户主动提问、版本明确且知识条目已审核 | 说明技能、装备作用与适用条件 | 不把一般机制解释冒充当前画面已经发生的事实 |
| 情境反馈与训练目标 | 有证据的事件、结束状态或赛后日志 | “这次后撤保住了状态；下一次继续先看队友位置。” | 结果因果不充分时只描述行为；鼓励性表达不虚构表现 |

所有例句都表示功能形式，只有前置条件满足才展示；它们不是对任意对局均有效的固定指令。

### 6.9 提醒仲裁、问答状态与风格

1. 同时出现多个候选建议时，优先处理迫近风险和原建议失效，其次是短时间有效的团战/资源准备，再是对线、出装和一般解释。频率上限与冷却时间可配置。
2. 主动提示关闭后，仍可持续采集并更新状态，只有用户提问才回复；“暂停观察”则停止采样并使动态建议失效。界面明确区分两个开关。
3. 问答绑定请求时的对局、状态版本、证据时间与观察范围；回答返回时再次校验。用户重复提问不沿用已经过期的战术结论。
4. “为什么这样建议”展示本条建议的必要依据和未知项。原因解释引用已确认事实，不能让文本模型自行补造隐藏技能或敌方位置。
5. 表达风格只改变长度、解释方式和语气，不改变行动结论、事实和未知项。鼓励话术放在低打扰时机，不给玩家贴负面标签。
6. 有可靠事件跟踪时，简短说明一条建议被撤销的原因；“未提醒”与“未在画面中看到”不等同于事件没有发生。

## 七、赛后数据摘要与过程回顾

流程调整为：识别结束阶段 → 等待结算页可见且稳定 → 提取当前可见字段 → 校验/合并 → 生成数据摘要 → 合成海报和二维码。

- 若用户未进入详细战绩页，生成当前可见数据的简版结果；不得声称完整取得十人战绩。
- 参团率只能由可靠的个人击杀、助攻和队伍总击杀等必要字段，按确认口径计算；分母为 0 时标为不适用。
- “经济转化”等指标必须定义公式并确认数据足够，否则移除。
- 官方 MVP 仅在界面明确显示时提取；模型生成的表现点评应与官方评定分开。
- 只有结算截图：写数据摘要与改进建议，不声称还原了关键团战或整局胜负原因。
- 有局中事件日志：引用具体时间和事件，明确未覆盖的阶段。事件日志至少保留事件时间、证据帧引用、已确认状态、建议、展示时间及可观察结果。
- “系统发出建议”不等于“用户执行建议”；没有可靠后续证据时不评价执行情况。
- 有合格行为记录时，战报加入一条具体回顾和下一局训练目标；无过程证据时只输出数据点评与通用练习。趣味评语围绕游戏行为，避免无依据地指定“背锅位”。
- 海报与二维码需校验访问地址是否能被手机访问，并说明访问有效期。

## 八、三周排期与验收

三周按单游戏、单路会话、团队能并行开展视觉/后端/前端工作的 Demo 排期。首期重点为 BP 对线候选、1 类对线事件、1 类团战准备/撤退事件、固定文字问答与赛后摘要；对位资料审核计入工期。其他新增功能按识别和延迟验证结果分批加入，不把全部团战与装备场景压进原三周承诺。60 位演示英雄不代表全部两两对位已验证。

| 周次 | 主要任务 | 验收与范围控制 |
| --- | --- | --- |
| 第 1 周 | 电脑窗口/桌面连续捕获与模型部署；自动阶段与分路识别；BP/对线字段识别；最新帧队列；HUD；确定英雄及同路对位资料覆盖子集 | 启动一次后连续更新视觉状态，记录捕获兼容性、完整 JSON 耗时、显存及对游戏性能的影响；形成已审核对线资料清单与卡片样式。 |
| 第 2 周 | 视觉对位变化触发 BP 更新；锁定后切换；1 类对线与 1 类团战准备/撤退事件；文字问答、依据展示和提醒开关 | 用录像及电脑游戏窗口实时捕获验证；事件冲突时仅显示优先建议，状态过期时撤销；主动关闭后仍可提问，暂停后不使用旧画面给出新决策。 |
| 第 3 周 | 结算自动识别与摘要、建议/事件日志、下一局训练目标、海报扫码；连续运行与故障测试 | 直接观察电脑游戏窗口，演示 BP → 加载 → 已支持局中提醒 → 战报链路，阶段切换与事件不依赖人工点击；有过程证据才输出具体行为回顾。时间不足时简化海报，进阶决策及自动追踪单独排期。 |

第 2 周建议拆分：周一完成视觉分路/对位确认与候选过滤，周二完成对线资料查询和锁定切换，周三完成已选对线事件与 1 类团战准备或撤退事件，周四完成固定文字问答、提醒开关、依据展示与过期机制，周五完成整段录像与电脑屏幕实时捕获联调。该安排以第一周必要字段识别及对位资料审核通过、视觉与界面开发可并行为前提；如事件未达标则收缩覆盖并调整交付时间，不用人工切场景冒充自动识别。全局阵容搭配和精细团中追踪单独排期。

验收至少包含：

1. **识别质量**：按游戏阶段和字段统计准确率、可用覆盖率、错误接受率；英雄分别报告单槽位和完整阵容全对率。拒绝所有结果不能算达标。
2. **事件质量**：人工标注事件，统计精确率、召回率、每小时误报数、重复卡片数和过期卡片数；分别报告各类事件。
3. **数据划分**：按完整对局划分调优集和测试集，避免相邻画面跨集合导致成绩虚高；覆盖皮肤、特效、遮挡和界面变化。
4. **延迟**：报告 P50/P95，并注明设备、分辨率、实际输入像素、输出长度和并发。记录从证据画面采集到 HUD 实际显示的时间，另测真实事件发生到提示的时间，计入抽样和连续确认等待。
5. **目标性质**：原文 300–600ms 视觉、2 秒建议、5 秒战报可保留为待验证优化目标；第一周压测后确定可验收数值。战报计时从完整结算页稳定可见开始。
6. **稳定与降级**：测试目标窗口关闭/最小化、切换全屏、DPI/分辨率变化、多显示器、捕获黑帧/中断、模型异常、API 超时/限流、JSON 非法和跨局重置；可先以连续 2 小时或 5 局作为 Demo 测试起点，记录实际完成量。
7. **用户效果**：记录提示是否来得及执行、是否打扰、是否易读和游戏使用者对建议的评价；不能用未经对照的胜率变化证明有效。
8. **成本与容量**：记录单局 API 次数/费用、视觉推理占用和多路竞争情况；同机部署时比较开启/关闭助教前后的游戏帧率与帧时间波动，并事先约定可接受影响。单路通过后再确定每台推理主机支持的席位数。
9. **BP 候选资格**：在已确认状态的测试用例中，不出现被禁用、按当前模式被占用、已知不可用或分路不适用的候选；用户锁定后不继续推荐换英雄。覆盖禁选变化、预选更换、用户锁定、候选不足和字段未知等场景。
10. **对线判断质量**：候选解释关联到有效的同路对位资料；评审清线、换血和等级/装备阶段是否适用，统计对位资料覆盖率与无合格候选比例。测试换线、对位未知、血量劣势、兵线改变和支援出现后能否调整或撤销压制判断；不以阵容评价、团战表现、全局胜率或模型自评分作为替代指标。
11. **行为回顾真实性**：未知轨迹、时间窗外行为和缺失结果均保留未知；人工补录或演示样本明确标注。首期若未上线自动追踪，不将人工演示计为自动识别通过。
12. **实时视觉闭环**：选定电脑窗口或区域并启动监测后，自动完成画面采样、阶段识别、BP 更新、已支持事件判断、卡片失效与结算触发。记录实际有效观测频率、状态新鲜度和事件到提示/撤销的延迟。必须包含直接观察电脑游戏画面的验收；手动截图、人工录入状态或点击模拟事件的演示不能替代该项。
13. **团战与互动**：分别检查队友未到、技能未知、前排阵亡、局部人数变化和团后兵线等场景；能区分准备、拉扯、撤退与转资源。切换风格不改变事实和行动结论；主动提示关闭与暂停观察具有不同效果；问答不返回过期战术。

采集到提示显示的延迟可以分解为：电脑画面捕获 + 裁剪/预处理 + 排队 + 视觉推理 + 状态/事件处理 + API + 传输渲染。异机推理额外计入图像编码与传输。真实事件到提示还要考虑抽样等待与连续确认。WebSocket 只解决最后的传输步骤。

## 九、现场使用与数据处理

只采集需要的游戏区域，避免把系统通知和其他应用内容发送到模型。外部 API 默认接收脱敏后的结构化游戏状态。原始截图/录像是否保存、保存多久和删除方式应明确配置；用于调试的证据按最小必要范围保留。公开分享战报时默认隐藏账号与聊天信息。

现场提供明确的观察目标选择、开始/暂停监测入口，并展示当前是否正在采集。采集目标固定在用户选择的窗口或区域；切换应用时不自动扩大为整个桌面。针对电竞室和具体游戏，核对实时辅助的适用规则；需要时可切换为训练或赛后分析模式。
